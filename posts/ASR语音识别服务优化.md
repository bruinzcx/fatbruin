## ASR 在 AI 作业中的位置

AI 作业小节录制时同步调 ASR 服务商把语音实时转文字；录完根据 ASR 结果算流畅度、语速评分；提交作业时把 ASR 结果一并上传服务端做 AI 分析。

**依赖链**：流畅度评分、语速评分、关键词分析、口头禅分析、停顿分析——**全部**建立在准确的 ASR 结果之上。ASR 不是辅助功能，是 AI 作业的地基。

## 三类问题

### 1. 热词 / 词库

生僻专业词、同音词需要人工校准，意味着服务商必须提供词库/热词能力。粒度诉求还在往下走：不同用户、不同企业、甚至**每一次识别过程**可能需要不同热词。

### 2. Socket 连接稳定性

各家服务商的实时识别方案都是 Socket 推流音频到厂商服务端。两个问题：

- **并发控制**：每家厂商有并发上限，新连接超限就连不上。可以联系服务商提额，但不能无限提。
- **网络波动**：端上 Socket 天然不可靠，短时通讯质量波动即超时断连。

### 3. 断连用户无感知 → 卡死业务主流程

**这条是最严重的**。ASR 断连时用户只能从"文字识别有没有显示"间接察觉。后果链条：

无 ASR 结果 → 流畅度/语速无数据（UI 显示一团迷雾）→ 若讲师开了提交作业最低分限制 → **该次录制无法提交** → 用户回到「上传视频作业」流程路径很远 → 大概率整次录制作废。

一个网络抖动，代价是用户的一整段录制。

## 为什么不能简单断线重连

重连看似显然，实则不成立。三个理由，逐层递进：

1. **时间轴断裂**：流畅度与停顿分析强依赖 ASR 返回的断句结果和 word 偏移时间。重连后新会话的起始时间重置为 0，拼不回原时间轴。
2. **本地补时间轴也不行**：即使本地维护录制绝对时间、只用 ASR 的相对时间做拼接——**断句本身依赖连续音频输入**。断开期间本地缓存音频、重连后再识别，拿到的断句必然错误，一定会在物理中断点产生特征断句。
3. **并发限制**：重连也不保证能连上。

**实证**：服务商 D v1（iOS）每 60s 中断重连一次。即使用户在该时间点毫无停顿，识别结果在每个 60s 处都有一个断句。非连续数据必然产生异常停顿，**导致流畅度分析直接不可用**。这是后来 站点 C/D/E 站点切服务商 C的直接动因。

> 核心结论：**ASR 断连不是网络问题，是数据连续性问题**。重连能恢复连接，恢复不了语义连续性。

## 四项优化

### 支持热词

按语言分服务商，三个平台各自选型：

| 语言 | 服务商 | 支持能力 |
|------|--------|----------|
| 中文 | 服务商 A | 临时热词列表 |
| 日文 | 服务商 B | 临时热词列表 + 热词词库 |
| 英文及其他 | 服务商 C | 临时热词 |

- 当前粒度：**以企业为维度**配置热词列表，服务端维护。
- 未来：下探到**以作业为维度**。

### 可观测性

- 各服务商 Socket/SDK 关键生命周期（初始化、开始识别、停止识别）与错误返回节点，全部上报 Kibana。
- **30s 周期心跳日志**，记录识别到的稳态结果文本长度——用文本长度证明服务真的在跑，而不只是连接没断。

### 错误降级

检测到 ASR 报错时走服务端兜底：把出问题的作业**从实时录制流程快速导向上传流程**，用服务端异步分析替代端上实时连接。用户满意当次录制就直接提交走上传，不满意可自行重录。

关键在于给用户一条出路，而不是让他卡在无法提交的死胡同里。

### 按站点和语言切换 ASR 服务

**切语言**：已支持——各站点阿波罗配置按语言下发 ASR 平台类型，APP 据此启动对应服务。

**切站点**：iOS 侧 ASR 服务按包区分，各站点包引入的 SDK 不同：

| 包 | 引入的 SDK |
|------|------------|
| 站点 A 包 | 服务商 A、服务商 B |
| 站点 B 包 | 服务商 B、服务商 D、服务商 C |
| 站点 C 包 | 服务商 B、服务商 D、服务商 C |

- 部分 SDK 因合规问题不可接入特定包；站点 F 只有服务商 D。
- 自研 ASR、服务商 E、服务商 B、服务商 C 四家支持切站点，按下发类型调起。
- **兜底策略**：站点 A 包用服务商 A 兜底，其他包用服务商 C 兜底。下发的服务在当前包缺失则走兜底。

iOS 于 2024.10 尝试把各站点 SDK 全部引入同一包，实现"切站点即切服务"（Android 已合并）。

**包体积担忧被实测证伪**：

| 阶段 | 站点 A Debug 包体积 |
|------|-----------------|
| 合并前 | 219 MB |
| 合并后 | 219 MB |

新引入服务商 E SDK + 多 SDK 合并，包体积基本无变化。

## 日志设计

所有 ASR 日志统一以 `<ASR 日志 key>` 为 key，Kibana 搜该 key 即可过滤全部 ASR 问题。

**准备阶段**
- 获取配置失败 → `refreshASRGlobalConfig fail`

**启动服务**
- `buildASRService` 时打一次，携带**服务端下发的平台类型**
- 初始化失败打一次（各 Service 按 SDK 初始化方式，时机不同）
- `buildASRService` 完成后打一次，携带 **APP 实际采用的 ASR 类型**（按类名区分）

> 下发类型与实际类型分两次打点，是为了让兜底降级在日志里可见——两者不一致即说明走了兜底。

**服务进行中**
- 正常：收到稳态识别结果后每 30s 上报心跳，携带文本长度
- 异常：SDK/Server 回调的错误码与错误信息

**服务结束**
- 打一次结束日志

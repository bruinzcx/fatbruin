**上下文工程：会话与记忆**
**作者：Kimberly Milam 和 Antonio Gulli**

## 简介

本白皮书探讨会话（Sessions）和记忆（Memory）在构建有状态的智能 LLM 智能体时所起的关键作用，帮助开发者打造更强大、更个性化、更具连续性的 AI 体验。要让大语言模型（LLM）记住信息、持续学习并提供个性化交互，开发者必须在上下文窗口内动态组装和管理信息，这个过程就叫上下文工程（Context Engineering）。

本白皮书涉及的核心概念概括如下：

**• 上下文工程（Context Engineering）：** 在 LLM 的上下文窗口内动态组装、管理信息，从而构建有状态的智能体。

**• 会话（Sessions）：** 承载与智能体一次完整对话的容器，按时间顺序保存对话历史，以及智能体的工作记忆。

**• 记忆（Memory）：** 负责长期持久化的机制。它跨多个会话提取并整合关键信息，让 LLM 智能体的体验连贯且个性化。

## 上下文工程

LLM 天生无状态。除了训练数据，它的推理和认知只局限于单次 API 调用时“上下文窗口”里的信息。这就带来一个根本问题：AI 智能体需要知道能执行哪些操作（操作指令），需要可供推理的证据和事实数据，还需要界定当前任务的即时对话信息。要构建能记忆、能学习、能个性化交互的有状态智能体，开发者必须在每一轮对话中重新构建这些上下文。为 LLM 动态组装和管理信息的这套做法，就叫上下文工程。

上下文工程是传统**提示工程（Prompt Engineering）**的演进。提示工程关注如何写出最优的系统指令，而这些指令往往是静态的。**上下文工程**则着眼于整个请求负载，根据用户、对话历史和外部数据，动态构建能感知状态的提示。它要有策略地挑选、概括和注入各类信息，尽量提高相关性、减少噪音。这些上下文大多由外部系统管理，比如 RAG 数据库、会话存储和记忆管理器。智能体框架负责协调这些系统，检索上下文并组装成最终提示。

可以把上下文工程看作智能体的 *mise en place*（法语，意为“就位准备”），也就是厨师开火前备齐、处理好所有食材的关键一步。如果只给厨师一份菜谱（提示），他只能拿手边随便什么食材凑出一顿还过得去的饭。但如果先确保他手里有合适的优质食材、专用厨具，并且清楚该怎么摆盘，他就能稳定地做出一道出色的定制菜。上下文工程的目标，是让模型恰好拿到完成任务最相关的信息，不多也不少。

上下文工程负责组装一份复杂的请求负载，其中可能包含多种组成部分：

**• 引导推理的上下文** 定义智能体的基本推理模式和可执行的操作，决定它如何行事：

**• 系统指令（System Instructions）：** 高层指令，规定智能体的角色、能力和约束。

**• 工具定义（Tool Definitions）：** 智能体与外部世界交互时可调用的 API 或函数的 schema。

**• 少样本示例（Few-Shot Examples）：** 精心挑选的示例，借助上下文学习引导模型的推理过程。

**• 证据与事实数据** 是智能体推理所依据的实质数据，既包括已有知识，也包括针对具体任务动态检索到的信息，是智能体作答的“证据”：

**• 长期记忆（Long-Term Memory）：** 跨多个会话积累下来的、关于用户或主题的持久化知识。

**• 外部知识（External Knowledge）：** 从数据库或文档中检索到的信息，通常借助检索增强生成（RAG）获取。

**• 工具输出（Tool Outputs）：** 工具返回的数据或结果。

**• 子智能体输出（Sub-Agent Outputs）：** 承担特定子任务的专职智能体返回的结论或结果。

**• 制品（Artifacts）：** 与用户或会话相关的非文本数据，比如文件、图片。

**• 即时对话信息** 让智能体立足于当前交互，明确眼下要完成的任务：

**• 对话历史（Conversation History）：** 当前交互的逐轮记录。

**• 状态 / 草稿区（State / Scratchpad）：** 智能体即时推理时用到的临时信息或中间计算结果。

**• 用户提示（User's Prompt）：** 当前需要回答的问题。

上下文必须动态构建，这一点至关重要。以记忆为例，它不是一成不变的：用户与智能体交互、或有新数据摄入时，都要有选择地检索和更新记忆。另外，有效的推理往往依赖上下文学习（in-context learning），即 LLM 从提示里的示例中学会如何完成任务。

相比硬编码的示例，智能体使用与当前任务相关的少样本示例时，上下文学习的效果更好。同理，外部知识也是由 RAG 工具根据用户当前的查询检索出来的。

构建上下文感知的智能体，最棘手的挑战之一是管理不断增长的对话历史。理论上，大上下文窗口的模型能处理很长的对话记录；但实际上，上下文越长，成本和延迟越高。而且模型还可能出现“**上下文腐化（context rot）**”：上下文越长，模型关注关键信息的能力越弱。上下文工程对此的解法，是用摘要、选择性裁剪或其他压缩手段动态改写历史，在控制总 token 数的同时保留关键信息，最终带来更稳健、更个性化的 AI 体验。

在智能体的运行循环中，每一轮对话都会重复这样一个过程：

![][image1]Figure 1. Flow of context management for agents

图 1. 智能体的上下文管理流程

**1. 获取上下文：** 智能体先检索上下文，比如用户记忆、RAG 文档和近期的对话事件。如果是动态检索，智能体会根据用户查询和其他元数据确定要检索哪些信息。

**2. 准备上下文：** 智能体框架动态构建本次 LLM 调用所需的完整提示。单个 API 调用可以是异步的，但准备上下文本身是阻塞的“热路径”：上下文没准备好，智能体就无法往下走。

**3. 调用 LLM 和工具：** 智能体反复调用 LLM 和所需的工具，直到生成给用户的最终回复。工具和模型的输出会追加到上下文中。

**4. 上传上下文：** 本轮收集到的新信息会上传到持久化存储。这一步通常在“后台”进行：智能体可以先结束执行，记忆整合等后处理工作异步完成。

这个生命周期的核心是两个基础组件：**会话**和**记忆**。**会话**管理单次对话的逐轮状态；**记忆**则负责长期持久化，跨多个会话提取并整合关键信息。

可以把会话想象成你为某个项目使用的工作台或书桌。工作时，桌上摆满了需要的工具、笔记和参考资料，一切触手可及，但都是临时的，只服务于手头这项任务。项目完成后，你不会把整张乱糟糟的桌子原封不动地塞进储藏室，而是开始整理记忆，就像往文件柜里归档。你翻看桌上的材料，扔掉草稿和重复的笔记，只把最关键、已定稿的文件放进贴好标签的文件夹。这样，文件柜就能一直保持整洁、可靠、高效，成为今后所有项目的可信信息来源，不会被工作台上临时的混乱塞满。这个类比正对应高效智能体的工作方式：会话是单次对话的临时工作台，记忆则是精心整理的文件柜，让智能体在之后的交互中能想起关键信息。

有了上下文工程的整体概念，接下来我们深入它的两个核心组件：会话和记忆。先从会话讲起。

## 会话

会话是上下文工程的基础元素，它封装了单次连续对话的即时对话历史和工作记忆。每个会话都是一份独立的记录，绑定到某个具体用户。借助会话，智能体可以在一次对话范围内保持上下文、给出连贯的回复。一个用户可以有多个会话，但每个会话都是某次交互的独立日志，彼此互不关联。每个会话包含两个关键部分：按时间排列的历史（**事件**）和智能体的工作记忆（**状态**）。

**事件**是构成对话的基本单元。常见的事件类型有：**用户输入**（用户发来的消息，可以是文本、音频、图片等）、**智能体回复**（智能体对用户的答复）、**工具调用**（智能体决定使用某个外部工具或 API），以及**工具输出**（工具调用返回的数据，智能体会据此继续推理）。

除了聊天历史，会话通常还带有一个**状态**，即结构化的“工作记忆”或草稿区，用来保存与当前对话相关的临时结构化数据，比如购物车里有哪些商品。

随着对话推进，智能体会不断往会话里追加新事件，也可能根据自身逻辑修改状态。

事件的结构类似于传给 Gemini API 的 `Content` 对象列表：每一项都带有 `role` 和 `parts`，代表对话中的一轮，也就是一个事件。

**Python**

```python
contents = [
    {
        "role": "user",
        "parts": [ {"text": "What is the capital of France?"} ]
    }, {
        "role": "model",
        "parts": [ {"text": "The capital of France is Paris."} ]
    }
]

response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=contents
)
```

生产环境中，智能体的执行环境通常是无状态的，请求结束后不会保留任何信息。因此，必须把对话历史保存到持久化存储中，用户体验才能连贯。开发阶段用内存存储就够了，但生产应用应该使用可靠的数据库来存储和管理会话。比如，可以把对话历史存到 Agent Engine Sessions 这类托管服务中。

## 不同框架和模型之间的差异

核心思路大同小异，但不同的智能体框架实现会话、事件和状态的方式各不相同。智能体框架负责为 LLM 维护对话历史和状态，用这些上下文构建 LLM 请求，并解析、存储 LLM 的响应。

智能体框架就像你的代码与 LLM 之间的通用翻译。作为开发者，你在每一轮对话中面对的都是框架统一的内部数据结构，而把这些结构转换成 LLM 要求的精确格式，这项关键工作由框架完成。这层抽象的价值在于，它把智能体逻辑和具体使用的 LLM 解耦，避免被供应商锁定。

![][image2]Figure 2: Flow of context management for agents

图 2：智能体的上下文管理流程

最终目标是生成 LLM 能理解的“请求”。对 Google 的 Gemini 模型来说，请求就是一个 `List[Content]`。每个 Content 对象都是一个类似字典的简单结构，包含两个键：`role` 表示说话方（"user" 或 "model"），`parts` 表示消息的实际内容（文本、图片、工具调用等）。

在发起 API 调用之前，框架会自动把内部对象（例如 ADK 的 `Event`）中的数据映射到 `Content` 对象对应的 role 和 parts 上。说到底，框架给开发者提供了一套稳定的内部 API，同时在幕后应对各家 LLM 复杂多样的外部 API。

**ADK** 使用显式的 `Session` 对象，里面包含一个 `Event` 对象列表和一个独立的状态对象。会话就像一个文件柜：一个文件夹放对话历史（事件），另一个放工作记忆（状态）。

**LangGraph** 没有正式的“会话”对象，状态本身就是会话。这个包罗一切的状态对象既保存对话历史（以 `Message` 对象列表的形式），也保存其他所有工作数据。传统会话是只追加的日志，LangGraph 的状态则不同，它是可变的。

状态可以被改写，历史压缩之类的策略也能修改记录。这在处理长对话和 token 上限时很有用。

## 多智能体系统的会话

在多智能体系统中，多个智能体分工协作，每个智能体专注于一项更小、更专门的任务。要让它们高效配合，就必须共享信息。如下图所示，系统架构决定了它们共享信息的通信模式。这套架构的一个核心问题，是系统如何处理会话历史，也就是所有交互的持久化日志。

![][image3]

图 3：不同的多智能体架构模式

在介绍管理会话历史的架构模式之前，先要把它和发给 LLM 的上下文区分开。会话历史可以看作整场对话永久、完整的记录；上下文则是为某一轮精心组织、发给 LLM 的信息负载。智能体构建上下文时，可能只从历史中摘取相关片段，也可能加上特殊格式（比如一段引导性前言）来引导模型的回复。本节关注的是智能体之间传递什么信息，而不一定是发给 LLM 的上下文。

智能体框架处理多智能体会话历史，主要有两种方式：一种是共享的统一历史，所有智能体都写入同一份日志；另一种是各自独立的历史，每个智能体保留自己的视角。选哪种取决于任务性质，以及希望智能体之间以什么方式协作。

在**共享统一历史**模式下，系统中所有智能体都从同一份对话历史读取事件，也把所有事件写进这份历史。每个智能体的消息、工具调用和观察结果，都按时间顺序追加到同一份中央日志。这种方式最适合紧密耦合、需要单一可信来源的协作任务，比如多步骤问题求解，前一个智能体的输出就是下一个的直接输入。即使共享历史，子智能体也可以在把日志交给 LLM 之前先做处理，比如只筛选出相关的事件子集，或者给每个事件打上标签，标明它由哪个智能体生成。

如果你用 ADK 基于 LLM 的委派机制把任务交给子智能体，子智能体产生的所有中间事件都会写进根智能体所在的同一个会话：

```python
from google.adk.agents import LlmAgent

# The sub-agent has access to Session and writes events to it.
# 子智能体可以访问 Session 并向其写入事件。
sub_agent_1 = LlmAgent(...)

# Optionally, the sub-agent can save the final response text (or structured
# output) to the specified state key.
# 可选地，子智能体可以将最终响应文本（或结构化输出）保存到指定的状态键。
sub_agent_2 = LlmAgent(
    ...,
    output_key="..."
)

# Parent agent.
# 父智能体。
root_agent = LlmAgent(
    ...,
    sub_agents=[sub_agent_1, sub_agent_2]
)
```

在**各自独立的历史模式**下，每个智能体维护一份私有的对话历史，对其他智能体而言就是一个黑盒。中间思考、工具调用、推理步骤等内部过程，都只保存在智能体自己的私有日志里，外部看不到。智能体之间只通过显式消息通信，共享的是最终输出，而不是过程。

这种交互通常有两种实现方式：智能体即工具（Agent-as-a-tool），或智能体间（A2A）协议。采用智能体即工具时，一个智能体像调用普通工具一样调用另一个智能体，传入输入，拿回一份完整独立的最终输出。采用 A2A 协议时，智能体之间通过结构化协议直接收发消息。

下一节会更详细地介绍 A2A 协议。

## 多个智能体框架之间的互操作

图 4：使用不同框架的多个智能体之间的 A2A 通信

框架使用各自的内部数据表示，这给多智能体系统带来一个关键的架构取舍：把智能体和 LLM 解耦的那层抽象，同时也把它和基于其他框架的智能体隔离开了。这种隔离在持久层被进一步固化。`Session` 的存储模型通常把数据库 schema 直接绑定到框架的内部对象上，导致对话记录僵化、难以迁移。结果是，用 LangGraph 构建的智能体无法原生解读基于 ADK 的智能体持久化下来的 `Session` 和 `Event` 对象，任务也就无法无缝交接。

为了协调这些彼此隔离的智能体，一种新兴的架构模式是智能体间（A2A）通信。它让智能体能够互发消息，却没有解决共享丰富上下文状态这个核心问题。每个智能体的对话历史都按各自框架的内部 schema 编码，所以任何携带会话事件的 A2A 消息，都要经过一层转换才能派上用场。

更稳健的互操作架构，是把共享知识抽象到一个与框架无关的数据层，比如记忆。`Session` 存储保存的是原始的、框架特有的对象（如 `Events` 和 `Messages`），记忆层保存的则是**经过处理**的规范化信息：从对话中提取出的摘要、实体、事实等关键信息，通常以字符串或字典的形式存储。记忆层的数据结构不依赖任何一个框架的内部数据表示，因此可以充当通用的公共数据层。借助这种模式，异构智能体无需定制转换器，就能共享同一份认知资源，实现真正的协同智能。

## 会话的生产环境考量

把智能体搬到生产环境时，会话管理系统必须从简单的日志升级为稳健的企业级服务。需要重点考虑三个方面：**安全与隐私、数据完整性和性能**。Agent Engine Sessions 这类托管会话存储，就是专门为满足这些生产需求而设计的。

## 安全与隐私

保护会话中的敏感信息是硬性要求，没有商量余地。**严格隔离**是最关键的安全原则。会话归单个用户所有，系统必须强制执行严格隔离（例如通过 ACL），确保任何用户都无法访问他人的会话数据。每一次访问会话存储的请求，都必须针对会话所有者完成身份验证和授权。

处理个人身份信息（PII）的最佳实践，是在会话数据写入存储之前先做脱敏。这是一项基础安全措施，能大幅降低数据泄露的风险和“爆炸半径”。借助 Model Armor 等工具确保敏感数据从不落盘，可以更轻松地满足 GDPR、CCPA 等隐私法规，也更能赢得用户信任。

## 数据完整性与生命周期管理

生产系统需要明确的规则，规定会话数据如何长期存储和维护。会话不应永久保留。可以设置生存时间（TTL）策略，自动删除不活跃的会话，以控制存储成本、减轻数据管理负担。这就需要一套清晰的数据保留策略，规定会话在归档或永久删除前要保留多久。

此外，系统必须保证各项操作按**确定的顺序**追加到会话历史中。事件的时间顺序正确，对话日志才算完整。

## 性能与可扩展性

会话数据处在每次用户交互的“热路径”上，所以性能是首要关注点。会话历史的读写必须非常快，才能保证用户体验流畅。智能体运行时通常是无状态的，每轮开始时都要从中央数据库拉取完整的会话历史，这会带来网络传输延迟。

要降低延迟，关键是减少传输的数据量。一项重要优化是在把会话历史发给智能体之前先做过滤或压缩。比如，可以删掉那些与当前对话状态无关的旧函数调用输出。下面几节会详细介绍几种压缩历史的策略，帮助有效管理长上下文对话。

## 管理长上下文对话：取舍与优化

在简单的架构里，会话就是用户与智能体之间一份不可变的对话日志。但对话越长，消耗的 token 就越多。现代 LLM 虽然能处理长上下文，但依然有限制，对延迟敏感的应用尤其如此：

**1. 上下文窗口限制：** 每个 LLM 一次能处理的文本量都有上限（即上下文窗口）。对话历史一旦超出这个上限，API 调用就会失败。

**2. API 成本（$）：** 大多数 LLM 提供商按收发的 token 数计费。历史越短，token 越少，每轮成本越低。

**3. 延迟（速度）：** 发给模型的文本越多，处理时间越长，用户等待回复的时间也越长。压缩能让智能体保持快速响应。

**4. 质量：** token 数增加后，上下文中多出来的噪音和自回归误差可能会拉低效果。

管理与智能体的长对话，就像一位精明的旅行者为长途旅行收拾行李箱。行李箱好比智能体有限的上下文窗口，衣物和随身物品则是对话中的一条条信息。如果什么都往里塞，箱子会又重又乱，想要的东西很难一下找到，这就像上下文窗口塞得太满，处理成本上升、响应变慢。反过来，如果带得太少，又可能落下护照或厚外套这类必需品，毁掉整趟旅程，这就像智能体丢失了关键上下文，给出无关或错误的答案。旅行者和智能体面临的约束是一样的：关键不在于能带多少，而在于只带需要的东西。

压缩策略用来缩减冗长的对话历史，让它装得进模型的上下文窗口，同时降低 API 成本和延迟。对话越长，每轮发给模型的历史就可能越大。压缩策略的做法是巧妙地裁剪历史，同时尽量保住最重要的上下文。

那么，怎么判断该从会话里丢掉**哪些**内容，又不丢失有价值的信息？可选的策略从简单的截断到复杂的压缩都有：

**• 保留最近 N 轮：** 最简单的策略。智能体只保留最近 N 轮对话（即“滑动窗口”），更早的内容全部丢弃。

**• 按 token 截断：** 把历史发给模型之前，智能体从最新的消息开始往回统计 token，在不超过预设上限（比如 4000 个 token）的前提下尽量多保留消息，更早的内容直接截掉。

**• 递归摘要：** 用 AI 生成的摘要替换对话中较早的部分。对话不断变长，智能体会定期额外调用一次 LLM，对最早的消息做摘要。这份摘要就是历史的压缩形式，通常作为前缀放在最近几轮的原文消息之前。

例如，可以用 ADK 应用内置的插件**保留最近 N 轮**，以限制发给模型的上下文。这不会修改会话存储中保存的历史事件：

```python
from google.adk.apps import App
from google.adk.plugins.context_filter_plugin import ContextFilterPlugin

app = App(
    name='hello_world_app',
    root_agent=agent,
    plugins=[
        # Keep the last 10 turns and the most recent user query.
        # 保留最后 10 轮和最近的用户查询。
        ContextFilterPlugin(num_invocations_to_keep=10),
    ],
)
```

复杂的压缩策略本来就是为了降低成本和延迟，所以递归摘要这类开销大的操作，必须放到后台异步执行，并把结果持久化。“放到后台”是为了不让客户端等待，“持久化”是为了避免重复做昂贵的计算。通常由智能体的记忆管理器负责生成并持久化这些递归摘要。智能体还要记录哪些事件已经并入了压缩摘要，避免把原本冗长的原始事件再白白发给 LLM。

此外，智能体还要决定**何时**压缩。触发机制大致分为以下几类：

**• 按数量触发**（即 token 大小或轮次阈值）：对话一旦超过预设阈值就压缩。管理上下文长度时，这种方法通常“够用”。

**• 按时间触发：** 触发压缩的不是对话长度，而是一段时间没有活动。如果用户停止交互一段时间（比如 15 或 30 分钟），系统可以在后台跑一次压缩任务。

**• 按事件触发**（即语义 / 任务完成）：智能体判断某个任务、子目标或对话话题已经结束时，决定触发压缩。

例如，可以用 ADK 的 `EventsCompactionConfig`，在达到配置的轮次后触发基于 LLM 的摘要：

**Python**

```python
from google.adk.apps import App
from google.adk.apps.app import EventsCompactionConfig

app = App(
    name='hello_world_app',
    root_agent=agent,
    events_compaction_config=EventsCompactionConfig(
        compaction_interval=5,
        overlap_size=1,
    ),
)
```

记忆生成是一种更宽泛的能力，指从冗长、嘈杂的数据源中提炼出持久的知识。本节介绍了从对话历史中提取信息的一个典型例子：会话压缩。压缩会提炼整场对话的原文记录，提取关键事实和摘要，丢掉对话中的寒暄和废话。

在压缩的基础上，下一节会更全面地讨论记忆的生成与管理，介绍创建、存储和检索记忆的各种方式，帮助智能体积累长期知识。

## 记忆

记忆和会话是深度共生的关系：会话是生成记忆的主要数据来源，记忆又是控制会话规模的关键手段。记忆是从对话或数据源中提取的有意义信息的快照。它是一种浓缩表示，保留了重要的上下文，供今后的交互使用。记忆通常跨会话持久保存，以提供连贯且个性化的体验。

“*记忆管理器*”作为一项专门的、解耦的服务，为多智能体互操作打下基础。记忆管理器常用与框架无关的数据结构，比如简单的字符串和字典。因此，基于不同框架构建的智能体都能接入同一个记忆存储，形成一个所有接入的智能体都能使用的共享知识库。

*注意：有些框架也会把会话或原文对话称为“短期记忆”。本白皮书中的记忆，特指提取出来的信息，而不是原始的逐轮对话。*

存储和检索记忆，是构建复杂智能体的关键。一套稳健的记忆系统能解锁几项关键能力，把普通聊天机器人变成真正的智能体：

**• 个性化：** 最常见的用法是记住用户的偏好、事实和过往交互，据此定制之后的回复。比如，记住用户最喜欢的球队，或者坐飞机时偏好的座位，体验就会更贴心、更个性化。

**• 上下文窗口管理：** 对话变长后，完整历史可能超出 LLM 的上下文窗口。记忆系统可以通过生成摘要或提取关键事实来压缩历史，不必每轮都发送成千上万个 token，也能保留上下文，从而降低成本和延迟。

**• 数据挖掘与洞察：** 以聚合、保护隐私的方式分析大量用户的记忆，可以从噪音中提炼出洞察。比如，零售聊天机器人可能发现很多用户都在问某款商品的退货政策，从而提示这里可能有问题。

**• 智能体自我改进与适应：** 智能体可以为自身表现建立程序性记忆，记录哪些策略、工具或推理路径带来了成功的结果，从而在过往运行中学习。这样它就能积累一套行之有效的解决方案手册，随着时间推移不断调整、提升解决问题的能力。

在 AI 系统中创建、存储和使用记忆是一个协作过程。技术栈中的每个组件，从最终用户到开发者的代码，都扮演着各自的角色。

**1. 用户：** 提供记忆的原始数据。有些系统允许用户直接提供记忆（比如通过表单）。

**2. 智能体（开发者逻辑）：** 决定记住什么、何时记住，并协调对记忆管理器的调用。在简单的架构里，开发者可以把逻辑写成*每次*都检索记忆、*每次*都触发生成。在更高级的架构里，可以把记忆实现为工具，由智能体（通过 LLM）自行决定何时检索或生成记忆。

**3. 智能体框架（如 ADK、LangGraph）：** 提供与记忆交互的结构和工具，扮演管道的角色。它规定开发者的逻辑如何访问对话历史、如何与记忆管理器交互，但本身不负责长期存储。它还规定检索到的记忆如何填入上下文窗口。

**4. 会话存储（如 Agent Engine Sessions、Spanner、Redis）：** 保存会话的逐轮对话。原始对话会被送进记忆管理器，用来生成记忆。

**5. 记忆管理器（如 Agent Engine Memory Bank、Mem0、Zep）：** 负责记忆的存储、检索和压缩，具体机制取决于所用的提供商。它是一个专门的服务或组件，接收智能体识别出的潜在记忆，并管理其整个生命周期：

**• 提取**：从源数据中提炼关键信息。

**• 整合**：梳理记忆，合并重复的实体。

**• 存储**：把记忆写入持久化数据库。

**• 检索**：取出相关记忆，为新的交互提供上下文

## 记忆类型

智能体的记忆可以按信息的存储方式和获取方式分类。不同类型的记忆协同工作，帮助智能体对用户及其需求形成丰富、贴合情境的理解。无论哪种记忆，都遵循同一条规则：记忆是描述性的，不是预测性的。

“记忆”是记忆管理器返回、供智能体用作上下文的最小上下文单元。具体 schema 可能各不相同，但一条记忆通常由两部分组成：**内容**和**元数据**。

**内容**是从源数据（即会话中的原始对话）里提取出的记忆主体。关键在于，内容的设计与框架无关，采用任何智能体都能轻松读取的简单数据结构。内容可以是结构化的，也可以是非结构化的。**结构化记忆**通常以字典、JSON 等通用格式存储，schema 一般由开发者定义，而不是由某个框架规定，例如 `{"seat_preference": "Window"}`。**非结构化记忆**是用自然语言描述的一段较长交互、一个事件或一个主题的要点，例如“用户偏好靠窗座位。”

**元数据**提供关于记忆本身的上下文，通常以简单字符串存储，可以包括记忆的唯一标识、记忆“所有者”的标识，以及描述记忆内容或数据来源的标签。

## 信息类型

除了基本结构，记忆还可以按所代表的知识类型分类。这种区分对理解智能体如何使用记忆至关重要。借鉴认知科学，记忆分为两大功能类别：**陈述性记忆**（*“知道是什么”*）和**程序性记忆**（*“知道怎么做”*）。

**陈述性记忆**是智能体掌握的事实、数据和事件，也就是它能明确说出来、“陈述”出来的所有信息。如果一条记忆回答的是“是什么”，它就是陈述性的。这一类既包括一般的世界知识（语义记忆），也包括具体的用户事实（实体 / 情景记忆）。

**程序性记忆**是智能体掌握的技能和工作流程。它通过隐式地示范如何正确完成任务来指导智能体的行动。如果一条记忆有助于回答“怎么做”，比如预订行程时应按什么顺序调用工具，它就是程序性的。

## 组织模式

记忆创建出来之后，接下来的问题是如何组织。记忆管理器通常采用以下一种或几种模式：集合、**结构化用户档案**或**“滚动摘要”**。这些模式决定了各条记忆之间以及记忆与用户之间如何关联。

集合模式把一个用户的内容组织成多条彼此独立的自然语言记忆。每条记忆都是一个独立的事件、摘要或观察，不过同一个大主题下也可能有多条记忆。借助集合，可以存储和搜索与特定目标或主题相关的、规模更大且结构较松散的信息。

**结构化用户档案**模式把记忆组织成关于用户的一组核心事实，就像一张不断用稳定的新信息更新的联系人卡片。它便于快速查找姓名、偏好、账户详情这类基础事实信息。

**“滚动”摘要**模式与结构化用户档案不同，它把所有信息整合成一条不断演进的记忆，用自然语言概括用户与智能体之间的整段关系。管理器不新建单独的记忆，而是持续更新这一份主文档。这种模式常用于压缩长会话，在控制总 token 数的同时保留关键信息。

## 存储架构

存储架构也是一项关键决策，它决定智能体检索记忆的速度和智能程度：是擅长查找概念相近的内容、理解结构化关系，还是两者兼顾。

记忆通常存储在**向量数据库**和 / 或**知识图谱**中。向量数据库用来查找与查询概念相近的记忆；知识图谱则把记忆存成由实体及其关系构成的网络。

**向量数据库**是最常见的做法，按语义相似度而不是精确关键词来检索。记忆被转换成嵌入向量，数据库从中找出与用户查询概念上最接近的结果。它特别擅长检索非结构化的自然语言记忆，这类场景看重的是上下文和含义（即“原子事实”）。

**知识图谱**把记忆存成由实体（节点）和关系（边）构成的网络。检索时遍历图，找出直接和间接的关联，让智能体能推理出不同事实之间如何相连。它非常适合结构化的关系查询，以及理解数据中的复杂关联（即“知识三元组”）。

也可以把两者结合成**混合方案**：为知识图谱中的结构化实体附加向量嵌入，让系统同时支持关系搜索和语义搜索。这样既有图的结构化推理能力，又有向量数据库细腻的概念搜索能力，两全其美。

## 创建机制

记忆还可以按创建方式分类，包括信息是如何得来的。**显式记忆**是用户直接命令智能体记住某件事时创建的（例如“记住我的纪念日是 10 月 26 日”）。**隐式记忆**则是智能体在没有直接命令的情况下，从对话中推断并提取信息而创建的（例如“我的纪念日就在下周，能帮我给伴侣挑件礼物吗？”）

记忆还可以按提取逻辑位于智能体框架内部还是外部来区分。**内部记忆**指直接内置在智能体框架中的记忆管理，上手容易，但通常缺少高级功能。内部记忆也可以使用外部存储，但生成记忆的机制在智能体内部。

**外部记忆**指使用一个独立的、专门负责记忆管理的服务（如 Agent Engine Memory Bank、Mem0、Zep）。智能体框架通过 API 调用这个外部服务来存储、检索和处理记忆。这种方式提供语义搜索、实体提取、自动摘要等更完善的功能，把记忆管理这项复杂工作交给专门打造的工具。

## 记忆作用域

你还要考虑记忆描述的是*谁*或*什么*。这决定了用哪个实体（**用户**、**会话**或**应用**）来聚合和检索记忆。

**用户级作用域**最常见，目的是为每个人提供连贯、个性化的体验，例如*“用户偏好中间座位。”* 记忆绑定到具体的用户 ID，在该用户的所有会话中持续存在，让智能体能长期了解用户的偏好和历史。

**会话级作用域**用于压缩长对话，例如*“用户正在购买 2025 年 11 月 7 日至 11 月 14 日往返纽约和巴黎的机票，偏好直飞航班和中间座位”*。它为单个会话中提炼出的洞察建立一份持久记录，让智能体可以用一组简洁的关键事实，替换冗长且

占用大量 token 的对话记录。关键在于，这种记忆不同于原始会话日志：它只包含从对话中提炼出的洞察，不包含对话本身，且其上下文仅限于该会话。

**应用级作用域**（即全局上下文）指应用的所有用户都能访问的记忆，例如*“代号 XYZ 指的是这个项目……”*。这一作用域用于提供共享上下文、广播全系统范围的信息，或建立

公共知识的基线。应用级记忆的一个常见用途是*程序性记忆*，为智能体提供“怎么做”的指令，通常是为了帮助智能体在服务所有用户时更好地推理。关键是，这类记忆必须清除所有敏感内容，防止数据在用户之间泄露。

## 多模态记忆

“多模态记忆”是一个关键概念，描述智能体如何处理图片、视频、音频等非文本信息。关键在于区分记忆*从何而来*的数据（**来源**）和记忆实际存储的数据（**内容**）。

**来自多模态来源的记忆**是最常见的实现。智能体可以处理文本、图片、音频等各种数据，但生成的记忆是从中提炼出的**文本洞察**。比如，智能体可以处理用户的语音备忘录来生成记忆。它不保存音频文件本身，而是把音频转写成文字，生成一条文本记忆，如“用户对最近的发货延迟感到不满。”

**包含多模态内容的记忆**是一种更高级的做法，记忆本身就包含非文本媒体。智能体不只是描述内容，而是直接保存内容。比如，用户上传一张图片并说“把这个记下来，作为我们的 logo 设计。”智能体就会创建一条直接包含该图片文件的记忆，并关联到用户的这条请求。

目前大多数记忆管理器侧重于处理多模态来源，生成的仍是文本内容。这是因为针对具体记忆生成和检索图片、音频这类非结构化二进制数据，需要专门的模型、算法和基础设施。把所有输入都转成文本这种通用、可搜索的格式，要简单得多。

例如，可以用 Agent Engine Memory Bank 从多模态输入生成记忆。输出的记忆是从内容中提取出的文本洞察：

下一节介绍记忆生成的机制，重点讲两个核心阶段：从源数据中提取新信息，以及把这些信息与已有的记忆库整合。

## 记忆生成：提取与整合

记忆生成会自动把原始对话数据转化为结构化、有意义的洞察。可以把它看作一条**由 LLM 驱动的 ETL（提取、转换、加载）流水线**，专门用来提取和压缩记忆。正是这条 ETL 流水线，让记忆管理器有别于 RAG 引擎和传统数据库。

开发者不必手动指定数据库操作，记忆管理器会用 LLM 智能判断何时新增、更新或合并记忆。这种自动化是记忆管理器的核心优势：它把管理数据库内容、串联多次 LLM 调用、部署后台数据处理服务等复杂工作都封装了起来。

![][image6]

图 6：记忆生成的高层算法：从新数据源中提取记忆，并与已有记忆整合

具体算法因平台而异（如 Agent Engine Memory Bank、Mem0、Zep），但记忆生成的整体流程通常分为四个阶段：

**1. 摄入：** 客户端把原始数据源（通常是对话历史）交给记忆管理器，流程由此开始。

**2. 提取与过滤：** 记忆管理器用 LLM 从源数据中提取有意义的内容。关键在于，这个 LLM 不会什么都提取，只提取符合预先定义的**主题定义**的信息。如果摄入的数据里没有与这些主题匹配的信息，就不会生成记忆。

**3. 整合：** 这是最复杂的阶段，记忆管理器要处理冲突和去重。它会执行一个“自我编辑”的过程，用 LLM 把新提取的信息与已有记忆做比对。为了让用户的知识库保持连贯、准确，并随新信息不断演进，管理器可以决定：

**• 合并**：把新洞察并入已有记忆。

**• 删除**：已有记忆已经失效时，将其删除。

**• 创建**：主题是全新的，就新建一条记忆。

**4. 存储：** 最后，新增或更新的记忆被写入持久化存储层（如向量数据库或知识图谱），供之后的交互检索。

Agent Engine Memory Bank 这类托管式记忆管理器能把这条流水线完全自动化。它们提供一个统一、连贯的系统，把对话中的杂乱信息转化为结构化知识，让开发者专注于智能体逻辑，而不必自己构建和维护底层数据基础设施。例如，用 Memory Bank 触发记忆生成，只需一次简单的 API 调用：

```python
from google.cloud import vertexai
client = vertexai.Client(project=..., location=...)
client.agent_engines.memories.generate(
name="projects/.../locations/...reasoningEngines/...",
scope={"user_id": "123"},
direct_contents_source={
"events": [...]
},
config={
# Run memory generation in the background.
"wait_for_completion": False
}
}
```

代码片段 6：用 Agent Engine Memory Bank 生成记忆

记忆生成的过程，好比一位勤快的园丁打理花园。提取就像收到新的种子和幼苗（对话中的新信息）。园丁不会随手把它们扔进地里，而是先做整合：拔掉杂草（删除冗余或冲突的数据），修剪疯长的枝条，让已有的植物长得更好（精炼和概括已有记忆），再把幼苗仔细种到最合适的位置。正是这种持续、用心的打理，让花园保持健康、有序，并随时间不断繁茂，而不是长成一片杂乱无用的荒草。这个异步过程在后台进行，保证花园随时可以迎接下一次到访。

接下来，我们深入看看记忆生成的两个关键步骤：提取和整合。

## 深入解析：记忆提取

记忆提取要回答一个根本问题：**“这次对话里，哪些信息有意义到值得成为记忆？”** 这不是简单的摘要，而是一个有针对性的智能过滤过程，目的是把信号（重要事实、偏好、目标）和噪音（寒暄、客套话）分开。

“有意义”没有统一标准，完全取决于智能体的目的和用例。客服智能体需要记住的（如订单号、技术问题），和私人健康教练需要记住的（如长期目标、情绪状态），根本不是一回事。因此，能自定义保留哪些信息，是打造真正好用的智能体的关键。

记忆管理器中的 LLM 依据一套精心设计的程序化护栏和指令来决定提取什么，这些护栏和指令通常写在一段复杂的系统提示里。这段提示给 LLM 提供一组主题定义，以此界定什么叫“有意义”。如果采用基于 schema 和模板的提取，就给 LLM 一个预定义的 JSON schema，或借助结构化输出等 LLM 能力提供模板，要求 LLM 用对话中的对应信息填充 JSON。另一种做法是用自然语言定义主题，用简单的自然语言描述来引导 LLM。

如果采用少样本提示，就用示例“演示”给 LLM 看该提取什么。提示里包含几段输入文本，以及每段应该提取出的理想、高保真记忆。LLM 从示例中学到所需的提取模式。对于难以用 schema 或简单定义描述的自定义主题或微妙主题，这种方法尤其有效。

大多数记忆管理器开箱即可识别常见主题，比如用户偏好、关键事实或目标。很多平台也允许开发者自定义主题，让提取过程贴合自己的业务领域。例如，可以提供自己的主题定义和少样本示例，自定义 Agent Engine Memory Bank 认为值得持久保存的信息：

记忆提取本身不是“摘要”，但算法可能会借助摘要来提炼信息。为了提高效率，很多记忆管理器会把对话的滚动摘要直接放进记忆提取

提示中。这份压缩后的历史提供了从最近交互中提取关键信息所需的上下文，不必每轮都重复处理完整冗长的对话来维持上下文。

从数据源中提取出信息后，还要通过整合来更新已有的记忆库，让它反映新信息。

## 深入解析：记忆整合

从冗长的对话中提取出记忆后，**整合**要把新信息融入一个连贯、准确、不断演进的知识库。它可以说是记忆生命周期中最复杂的阶段，能把零散的事实集合变成对用户经过梳理的理解。没有整合，智能体的记忆很快就会沦为一份把捕获过的每条信息都堆在一起的日志，嘈杂、矛盾、不可靠。这种“自我梳理”通常由 LLM 负责，正是它让记忆管理器超越了简单的数据库。

整合要解决对话数据带来的几个根本问题，包括：

**• 信息重复：** 用户可能在不同对话中用不同说法提到同一件事（比如先说“我需要一张飞纽约的机票”，后来又说“我打算去纽约旅行”）。简单的提取流程会生成两条重复的记忆。

**• 信息冲突：** 用户的情况会随时间变化。没有整合，智能体的记忆里就会出现相互矛盾的事实。

**• 信息演变：** 一个简单的事实可能变得更具体。最初的记忆“用户对营销感兴趣”，可能演变为“用户正在牵头一个营销项目，重点是第四季度的获客。”

**• 记忆相关性衰减：** 不是所有记忆都永远有用。智能体必须学会**遗忘**，主动**清理**陈旧、过时或置信度低的记忆，让知识库保持相关和高效。遗忘可以通过指示 LLM 在整合时优先采用较新的信息来实现，也可以通过生存时间（TTL）自动删除来实现。

整合是一个由 LLM 驱动的工作流，负责把新提取的洞察与用户已有的记忆做比对。第一步，工作流先检索与新记忆相似的已有记忆，作为整合的候选。如果某条已有记忆被新信息推翻，它可能被删除；如果被新信息补充，它可能被更新。

第二步，把*已有记忆*和*新信息*一起交给 LLM。它的核心任务是综合分析两者，决定该执行什么操作。主要操作有：

**• 更新：** 用新的或更正后的信息修改已有记忆。

**• 创建：** 新洞察是全新的、与已有记忆无关时，新建一条记忆。

**• 删除 / 作废：** 新信息让旧记忆完全失去意义或变得错误时，将其删除或作废。

最后，记忆管理器把 LLM 的决策转换为事务，更新记忆存储。

## 记忆来源追溯

机器学习有句经典格言：*“垃圾进，垃圾出”*。这对 LLM 更加要紧，结果往往是*“垃圾进，自信满满的垃圾出”*。要让智能体做出可靠决策、让记忆管理器有效整合记忆，它们都必须能审慎评估自身记忆的质量。这种可信度直接取决于记忆的**来源追溯（provenance）**，也就是对记忆出处和演变历史的详细记录。

![][image7]

图 7：数据源与记忆之间的信息流。一条记忆可以来自多个数据源，一个数据源也可以贡献多条记忆。

**记忆整合**会把多个来源的信息合并成一条不断演进的记忆，因此需要追踪记忆的血缘。如上图所示，一条记忆可能融合了多个数据源，一个数据源也可能被拆分成多条记忆。

为了评估可信度，智能体必须追踪每个来源的关键细节，比如出处（来源类型）和时效（“新鲜度”）。这些细节之所以关键，有两个原因：它们决定了整合记忆时每个来源占多大权重，也决定了智能体推理时该在多大程度上依赖这条记忆。

来源类型是判断可信度最重要的因素之一。数据源主要分为三类：

**• 引导数据：** 从内部系统（如 CRM）预先加载的信息。这类数据可信度高，可以用来初始化用户的记忆，解决冷启动问题，也就是如何为智能体从未接触过的用户提供个性化体验。

**• 用户输入：** 既包括用户显式提供的数据（比如通过表单，可信度高），也包括从对话中隐式提取的信息（通常不那么可信）。

**• 工具输出：** 外部工具调用返回的数据。一般不建议用工具输出生成记忆，因为这类记忆往往脆弱、容易过时，这种来源更适合做短期缓存。

## 记忆管理中的血缘追踪

这种动态、多来源的记忆方式，在管理记忆时会带来两个主要的运维挑战：**冲突解决**和**删除派生数据**。

记忆整合难免会遇到不同数据源相互冲突的情况。借助记忆的来源追溯，记忆管理器可以为信息来源建立信任等级。当来自不同来源的记忆相互

矛盾时，智能体必须依据这个等级来解决冲突。常见策略包括：优先采信最可靠的来源、优先采用最新的信息，或在多个数据点之间寻找相互印证。

管理记忆的另一个挑战出现在删除时。一条记忆可能来自多个数据源。用户撤销对某个数据源的授权后，由该来源派生的数据也应删除。但把该来源“沾过”的每条记忆都删掉，可能过于激进。更精确的做法是只用剩下的有效来源从头重新生成受影响的记忆，只是计算成本更高。

除了静态的来源信息，对记忆的置信度也必须不断变化。得到印证时置信度上升，比如多个可信来源给出一致的信息。但一个高效的记忆系统还必须通过记忆清理，主动梳理已有知识，也就是识别并“遗忘”那些不再有用的记忆。触发清理的因素有以下几种：

**• 随时间衰减：** 记忆的重要性可能随时间降低。两年前一次会议的记忆，可能不如上周的有用。

**• 置信度低：** 由薄弱推断得出、且从未被其他来源印证的记忆，可能会被清理。

**• 不再相关：** 随着智能体对用户的了解越来越深入，它可能判断一些较早的、琐碎的记忆已经与用户当前的目标无关。

把被动响应的整合流水线和主动清理结合起来，记忆管理器就能确保智能体的知识库不只是一份把说过的话越堆越多的日志，而是对用户经过梳理、准确且相关的理解。

## 推理时的血缘追踪

除了在梳理记忆库内容时考虑记忆的血缘，推理时也应考虑记忆的可信度。智能体对记忆的置信度不应一成不变，而要随着新信息和时间推移而变化。得到印证时置信度上升，比如多个可信来源给出一致的信息。反过来，旧记忆逐渐过时，置信度会随时间下降（衰减）；出现矛盾信息时，置信度也会下降。最终，系统可以通过归档或删除低置信度记忆来实现“遗忘”。这个动态的置信度分数在推理时至关重要。记忆及其置信度分数（如果有）不会展示给用户，而是注入到提示中，让 LLM 能评估信息的可靠性，做出更周全的决策。

整套信任机制都服务于智能体内部的推理过程。记忆及其置信度分数通常不会直接展示给用户，而是注入系统提示，让 LLM 权衡证据、考虑信息的可靠性，最终做出更周全、更可信的决策。

## 触发记忆生成

一旦触发生成，记忆管理器会自动完成记忆的提取和整合，但何时尝试生成记忆，仍需由智能体决定。这是一项关键的架构选择，需要在数据新鲜度与计算成本、延迟之间取得平衡。这个决策通常由智能体的逻辑掌控，可以采用多种触发策略。记忆生成可以由以下几类事件启动：

**• 会话结束：** 在多轮会话结束时触发生成。

**• 按轮次节奏：** 每隔固定轮次运行一次（比如每 5 轮）。**• 实时：** 每一轮结束后都生成记忆。

**• 显式命令：** 用户直接下达命令时启动（比如“记住这个”）

选择哪种触发方式，本质上是在成本和保真度之间取舍。**高频生成**（比如实时）能让记忆非常详细、新鲜，捕捉对话中的每个细节，但 LLM 和数据库的成本也最高，处理不当还可能增加延迟。**低频生成**（比如会话结束时）成本更低，但记忆的保真度可能偏低，因为 LLM 要一次性概括一大段对话。还要注意别让记忆管理器重复处理同一批事件，否则会带来不必要的成本。

## 后台操作与阻塞操作

记忆生成开销很大，需要调用 LLM 并写入数据库。对于生产环境中的智能体，记忆生成几乎都应该**放在后台异步处理**。

智能体把回复发给用户之后，记忆生成流水线可以并行运行，不阻塞用户体验。这种解耦对保持智能体的速度和响应感至关重要。如果采用阻塞（同步）方式，用户必须等记忆写完才能收到回复，体验会慢得让人无法接受，也让人恼火。因此，记忆生成需要放在一个在架构上独立于智能体核心运行时的服务中。

## 记忆检索

记忆生成机制就位后，关注点就可以转向同样关键的检索。智能的检索策略对智能体的表现至关重要，包括检索哪些记忆、何时检索。

检索记忆的策略在很大程度上取决于记忆的组织方式。对于**结构化用户档案**，检索通常就是直接查找整份档案或某个属性。但对于**记忆集合**，检索是一个复杂得多的搜索问题，目标是从大量非结构化或半结构化数据中，找出概念上最相关的信息。本节讨论的策略，正是为了应对记忆集合这类复杂的检索挑战。

记忆检索要为当前对话找出最相关的记忆。检索策略是否有效至关重要：塞进无关的记忆可能干扰模型、降低回复质量，而找到恰到好处的上下文，则能让交互显得非常聪明。核心挑战是在严格的延迟预算内，权衡记忆的“有用程度”。

高级记忆系统不止于简单搜索，而是从多个维度给候选记忆打分，找出最佳匹配：

**• 相关性（语义相似度）：** 这条记忆与当前对话在概念上有多相关？

**• 新近性（时间）：** 这条记忆是多久之前创建的？

**• 重要性（显著性）：** 这条记忆总体上有多关键？与相关性不同，记忆的“重要性”可以在生成时就确定。

只依赖向量相关性是一个常见误区。相似度分数可能会把概念相近、但陈旧或琐碎的记忆排到前面。最有效的策略是综合这三个维度打分的混合方法。

对于准确性压倒一切的应用，可以借助查询重写、重排序或专用检索器等方法优化检索。但这些技术计算成本高，会明显增加延迟，不适合大多数实时应用。如果场景确实需要这些复杂算法，而记忆又不会很快过时，加一层缓存是有效的缓解手段：把开销大的检索结果暂存起来，后续相同的请求就不必再承担高延迟。

**查询重写**是用 LLM 改进搜索查询本身。可以把用户含糊的输入**改写**成更精确的查询，也可以把一个查询**扩展**成多个相关查询，覆盖主题的不同方面。这能显著提升初始搜索结果的质量，但在流程一开始就多了一次 LLM 调用的延迟。

重排序的做法是：先用相似度搜索粗筛出一批候选记忆（比如前 50 条），再让 LLM 对这个较小的集合重新评估、重新排序，得到更准确的最终列表。

最后，还可以通过微调训练一个**专用检索器**。不过这需要标注数据，成本也可能大幅增加。

归根结底，最好的检索始于更好的记忆生成。确保记忆库质量高、没有无关信息，是让检索出的记忆都有用的最有效方法。

## 检索时机

检索的最后一项架构决策是*何时*检索记忆。一种做法是**主动检索**，每轮开始时自动加载记忆。这样上下文始终可用，但对于用不到记忆的轮次，会平白增加延迟。好在记忆在一轮之内不会变化，可以高效地缓存起来，抵消这部分性能开销。

例如，在 ADK 中，可以用内置的 `PreloadMemoryTool` 或自定义回调实现主动检索：


## 用记忆辅助推理

检索到相关记忆后，最后一步是有策略地把它们放进模型的上下文窗口。这一步很关键：记忆放在哪里，会显著影响 LLM 的推理和运行成本，最终决定答案的质量。

记忆主要有两种呈现方式：附加到系统指令中，或注入对话历史。实践中，混合策略通常最有效。对于需要始终存在的稳定全局记忆（如用户档案），放进**系统提示**；对于只与当前对话上下文相关的临时情景记忆，则用**对话注入**或**记忆即工具**。这样既满足了对持久上下文的需要，又保留了即时检索信息的灵活性。

## 放在系统指令中的记忆

用记忆辅助推理，一个简单的做法是把记忆附加到系统指令里。检索到的记忆连同一段前言直接附加到系统提示中，作为整场交互的基础上下文，对话历史因此保持干净。例如，可以用 Jinja 把记忆动态加入系统指令：

```python
from jinja2 import Template
template = Template("""
{{ system_instructions }}}
<MEMORIES>
Here is some information about the user:
{% for retrieved_memory in data %}* {{ retrieved_memory.memory.fact }} {% endfor %}</MEMORIES>
""")
prompt = template.render(
system_instructions=system_instructions,
data=retrieved_memories
)
```

把记忆放进系统指令，会赋予记忆很高的权威性，也能把上下文和对话清楚地分开，非常适合用户档案这类稳定的“全局”信息。但这样做有**过度影响**的风险：智能体可能会试图把每个话题都和核心指令里的记忆扯上关系，哪怕并不合适。

这种架构模式还有几个限制。首先，它要求智能体框架支持在每次调用 LLM 前动态构建系统提示，而这并不总是容易实现。其次，它与*“记忆即工具”*不兼容，因为在 LLM 能决定调用记忆检索工具之前，系统提示就必须定稿。最后，它不擅长处理非文本记忆。大多数 LLM 的系统指令只接受文本，很难把图片、音频这类多模态内容直接嵌进提示。

## 放在对话历史中的记忆

这种做法把检索到的记忆直接注入逐轮对话中，可以放在完整对话历史之前，也可以放在用户最新的查询之前。

不过，这种做法可能引入噪音、增加 token 成本，如果检索到的记忆不相关，还可能干扰模型。它的主要风险是**对话注入**：模型可能误以为这些记忆是对话中真实说过的话。还要特别注意注入的记忆用的是什么视角，比如使用“user”角色和用户级记忆时，记忆应该用第一人称来写。

## 程序性记忆

本白皮书主要讨论陈述性记忆，这也反映了当前商用记忆产品的现状。大多数记忆管理平台的架构也是围绕陈述性记忆设计的，擅长提取、存储和检索“是什么”，即事实、历史和用户数据。

然而，这些系统并不是为管理程序性记忆而设计的。程序性记忆是改进智能体工作流和推理的机制。存储“怎么做”不是信息检索问题，而是推理增强问题。管理这种“知道怎么做”的知识，需要一套完全独立、专门的算法生命周期，尽管它的整体结构与陈述性记忆相似：

**1. 提取：** 程序性提取需要专门设计的提示，从成功的交互中提炼出可复用的*策略*或“操作手册”，而不只是记录事实或有意义的信息。

**2. 整合：** 陈述性整合合并的是相关事实（“是什么”），程序性整合梳理的则是工作流本身（“怎么做”）。这是一个主动管理逻辑的过程，重点是把新的成功做法融入已有的“最佳实践”，修补已知方案中有缺陷的步骤，并清理过时或无效的流程。

**3. 检索：** 目标不是检索数据来回答问题，而是检索一份方案，指导智能体完成复杂任务。因此，程序性记忆的数据 schema 可能与陈述性记忆不同。

智能体这种“自我进化”逻辑的能力，自然会让人把它和一种常见的适应方法相比较：微调，通常借助人类反馈强化学习（RLHF）。两者都旨在改进智能体的行为，但它们的机制

和用途截然不同。微调是一个较慢的离线训练过程，会改变模型权重。程序性记忆则把合适的“操作手册”动态注入提示，借助上下文学习引导智能体，实现快速的在线适应，完全不需要微调。

## 测试与评估

有了带记忆的智能体，接下来要通过全面的质量测试和评估来验证它的行为。评估智能体的记忆是一个多层次的过程，需要验证三件事：智能体记住的东西对不对（质量），需要时能不能找到这些记忆（检索），以及用了这些记忆是否真的有助于达成目标（任务成功）。学术界关注可复现的基准测试，业界评估则更关心记忆如何直接影响生产环境中智能体的性能和可用性。

**记忆生成质量**指标评估记忆本身的内容，回答的问题是：**“智能体记住的东西对吗？”** 通常的测量方法是，把智能体生成的记忆与人工整理的理想记忆“黄金集”做比较。

**• 精确率：** 智能体创建的所有记忆中，准确且相关的占多大比例？精确率高，可以防止“过于积极”的记忆系统用无关噪音污染知识库。

**• 召回率：** 本应从源数据中记住的所有相关事实里，智能体记住了多大比例？召回率高，能确保智能体不遗漏关键信息。

**• F1 分数：** 精确率和召回率的调和平均数，用一个数字均衡地衡量质量。

**记忆检索性能**指标评估智能体能否在正确的时间找到正确的记忆。

**• Recall@K：** 需要某条记忆时，它是否出现在前 K 个检索结果中？这是衡量检索系统准确性的主要指标。

**• 延迟：** 检索处在智能体响应的“热路径”上。整个检索过程必须控制在严格的延迟预算内（比如 200 毫秒以下），以免拖累用户体验。

**端到端任务成功率**指标是最终检验，回答的问题是：“记忆真的帮智能体把工作做得更好了吗？”测量方法是评估智能体借助记忆完成下游任务的表现，通常用一个 LLM“评委”把智能体的最终输出与标准答案做比较。评委判断智能体的回答是否准确，从而有效衡量记忆系统对最终结果的贡献。

评估不是一次性的事，而是持续改进的引擎。上述指标提供了必要的数据，帮助你发现薄弱环节，并持续、系统地改进记忆系统。这个迭代过程包括：建立基线、分析失败案例、调整系统（比如改进提示、调整检索算法），再重新评估，衡量改动带来的影响。

上述指标关注的是质量，但能否上生产还取决于性能。对每个评估领域，都必须测量底层算法的延迟，以及在负载下的扩展能力。在“热路径”上检索记忆，可能要求严格控制在亚秒级。生成和整合虽然通常是异步的，但也必须有足够的吞吐量跟上用户需求。说到底，一个成功的记忆系统必须足够智能、高效、稳健，经得起真实场景的使用。

## 记忆的生产环境考量

除了性能，把带记忆的智能体从原型推向生产，还必须关注企业级的架构问题。这一转变对可扩展性、弹性和安全性提出了关键要求。生产级系统不仅要设计得智能，还要达到企业级的稳健性。

为了确保用户体验永远不被计算密集的记忆生成过程阻塞，稳健的架构必须把记忆处理与主应用逻辑解耦。这虽然是一种事件驱动的模式，但通常是通过直接、非阻塞地调用专用记忆服务的 API 来实现，而不是自己维护消息队列。流程如下：

**1. 智能体推送数据：** 发生相关事件后（比如会话结束），智能体应用以非阻塞方式调用记忆管理器的 API，“推送”原始数据（如对话记录）待处理。

**2. 记忆管理器在后台处理：** 记忆管理器服务立即确认请求，把生成任务放进自己内部托管的队列，然后独自承担异步的繁重工作：调用 LLM 提取、整合和格式化记忆。管理器也可能等到一段时间无活动之后，再处理这些事件。

**3. 持久化记忆：** 服务把最终的记忆（可能是新条目，也可能是对已有条目的更新）写入专用的持久化数据库。托管记忆管理器自带存储。

**4. 智能体检索记忆：** 之后，主智能体应用需要为新的用户交互获取上下文时，可以直接查询这个记忆存储。

这种基于服务的非阻塞方式，能保证记忆流水线中的故障或延迟不会直接影响面向用户的应用，让系统更有弹性。它也为选择**在线**（实时）生成还是**离线**（批量）处理提供了依据：前者适合保持对话的新鲜度，后者适合用历史数据为系统预填充记忆。

随着应用规模增长，记忆系统必须能稳定处理高频事件。面对**并发**请求，系统必须防止多个事件同时修改同一条记忆时出现死锁或竞态条件。可以用事务型数据库操作或乐观锁来缓解竞态条件，但当多个请求同时修改同一条记忆时，这可能会带来**排队**或**限流**。要缓冲大量事件、避免记忆生成服务被压垮，一个稳健的消息队列必不可少。

记忆服务还必须能扛住瞬时错误（**故障处理**）。如果 LLM 调用失败，系统应使用指数退避重试，并把持续失败的任务转入死信队列以便分析。

对于全球化应用，记忆管理器必须使用内置**多区域复制**的数据库，以保证低延迟和高可用。客户端复制行不通，因为整合需要一份单一、事务一致的数据视图，才能避免冲突。因此，记忆系统必须在内部处理复制，对开发者呈现为单一的逻辑数据存储，同时保证底层知识库全局一致。

Agent Engine Memory Bank 这类托管记忆系统，应该能帮你解决这些生产问题，让你专注于智能体的核心逻辑。

## 隐私与安全风险

记忆源自用户数据，本身也包含用户数据，因此需要严格的隐私和安全管控。可以打个比方：把系统的记忆想象成一座安全的企业档案馆，由专业的档案管理员打理，他的职责是保存有价值的知识，同时保护公司。

这座档案馆的首要规则是数据隔离。档案管理员绝不会把不同部门的机密文件混在一起，同理，记忆也必须在用户或租户级别严格隔离。服务某个用户的智能体，绝不能访问其他用户的记忆，这一点要通过严格的访问控制列表（ACL）来保证。此外，用户必须能以程序化方式控制自己的数据，有明确的选项可以退出记忆生成，或要求从档案中删除自己的全部文件。

归档任何文件之前，档案管理员都会执行关键的安全步骤。首先，逐页仔细检查，对敏感的个人信息（PII）做脱敏，既保存了知识，又不留下隐患。其次，档案管理员受过训练，能识别并丢弃伪造或刻意误导的文件，这是防范记忆投毒的保障。同样，系统必须先验证和清洗信息，再写入长期记忆，防止恶意用户通过提示注入破坏智能体的持久知识。系统必须配备 Model Armor 这类防护措施，在信息写入长期记忆之前先验证和清洗。

此外，如果多个用户共享同一组记忆，比如程序性记忆（教智能体如何做某件事），就存在泄露风险。例如，把一个用户的程序性记忆用作另一个用户的示例，就像在全公司范围内传阅一份备忘录，档案管理员必须先做严格的匿名化，防止敏感信息越过用户边界泄露。

## 结论

本白皮书探讨了**上下文工程**这门学问，重点介绍了它的两个核心组件：**会话**和**记忆**。从简单的一轮轮对话，到持久、可落地的智能，这条路要靠上下文工程来实现：把对话历史、记忆、外部知识等所有必要信息，动态组装进 LLM 的上下文窗口。整个过程依赖两套不同但相互关联的系统协同运作：即时的会话和长期的记忆。

**会话**掌管“当下”，是单次对话低延迟、按时间排序的容器。它面临的主要挑战是性能和安全，要求**低延迟访问**和**严格隔离**。为了避免上下文窗口溢出、延迟过高，必须用**提取**类技术（如按 token 截断或递归摘要）来**压缩**会话历史*内*或单次请求负载内的内容。此外，安全至关重要，会话数据持久化之前必须先做 **PII 脱敏**。

**记忆**是**长期个性化**的引擎，也是跨多个会话持久保存信息的核心机制。RAG 让智能体成为*事实*专家，记忆则更进一步，让它成为*用户*专家。记忆是一条主动的、由 LLM 驱动的 ETL 流水线，负责**提取、整合和检索**，从对话历史中提炼最重要的信息。通过**提取**，系统把最关键的信息提炼成要点记忆。接着，**整合**对这些新信息进行梳理，融入已有的记忆库，解决冲突、删除冗余数据，保证知识库连贯一致。为了保持流畅的用户体验，记忆生成必须在智能体回复之后，以**异步后台进程**的方式运行。通过追踪**来源**，并针对记忆投毒等风险采取防护措施，开发者就能构建出可信、自适应、真正能与用户共同学习和成长的助手。

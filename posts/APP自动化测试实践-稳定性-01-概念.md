## 一、稳定性测试到底在测什么？

稳定性测试关注三件事：App 会不会死，会不会越用越卡直到被系统杀掉，会不会让用户觉得卡。三者缺一不可。

### Crash：App 会不会死

这是最直观的一项。用户正在使用，App 突然退出，就是 Crash。

作为 iOS 开发，对它再熟悉不过：Xcode 的 Organizer 里能看到崩溃报告，TestFlight 和 App Store 上用户的崩溃也会聚合在那里。但这些都是**事后**的数据，用户已经崩了，我们才知道。稳定性框架要解决的是另一个问题：在发布给用户之前，主动用机器操作 App 成千上万次，把藏在角落里的崩溃路径提前暴露出来。

不妨做个对比：让一位 QA 用 App 一小时，和让机器以远超人类的速度连续操作几个小时，后者能触达的边界情况，远不是前者能覆盖的。

### 内存：App 会不会越用越卡，最后被系统杀掉

OOM 是 Out of Memory 的缩写，指内存不足。iOS 在内存压力过大时会直接强杀进程，用户看到的同样是 App 突然退出。**它和 Crash 的表现一模一样，原因却完全不同**，崩溃日志里也找不到代码层面的错误栈。

内存问题的特点是**有时间性**。启动时一切正常，用了半小时，内存悄悄涨到 800MB，然后被系统杀掉。常规的功能测试每条用例只跑几分钟，很难发现这类问题。这也是稳定性测试要长时间运行的原因：给内存泄漏足够的时间暴露自己。我们的夜间任务会用两个测试账号各连续跑 5 个小时。

### FPS 与卡顿：App 会不会让用户觉得卡

FPS 是 Frames Per Second，即每秒渲染的帧数。60Hz 的屏幕每秒要画 60 帧，每帧只有 16.67 毫秒的预算，一旦超时，用户就会感到卡顿。

这项指标的隐蔽之处在于，**功能完全正确的代码也可能导致卡顿**。比如在主线程上做了一次耗时的计算，界面冻结了 200 毫秒，业务逻辑没有任何 Bug，用户体验却很糟。

## 二、Monkey 测试：为什么要用"猴子"来测 App？

我们框架里最核心的工具叫 **Fastbot**，它属于 Monkey 测试工具。

"Monkey 测试"这个名字来自一个思想实验：让一只猴子在键盘上随机乱敲，只要时间足够长，它总会碰巧敲出某个 Bug。Monkey 测试的核心思想正是如此：用随机或半随机的方式大量模拟用户操作，让 App 在开发者没有预想到的操作序列中暴露问题。

这和按剧本执行的 UI 自动化测试有本质区别：

| | UI 自动化测试 | Monkey 测试 |
|---|---|---|
| 操作方式 | 按剧本执行固定步骤 | 随机或半随机地探索 |
| 验证目标 | 特定功能流程是否正确 | 任意操作下是否崩溃 |
| 覆盖范围 | 已知路径 | 未知路径（边界情况） |
| 适合发现 | 业务逻辑 Bug | Crash、内存问题、ANR |

可以这样理解：UI 自动化测试是"有针对性的检查"，Monkey 测试是"无差别的压力轰炸"。两者不是替代关系，而是互补的。

### Fastbot 比原版 Monkey 聪明在哪

Android 自带一个 `adb shell monkey` 工具，它是完全随机的：随机点、随机滑，根本不关心屏幕上有什么。纯随机的问题很明显：它可能在登录页上反复乱点，走不进任何业务页面；更糟的是，它可能误触"退出登录"、"删除账号"这类破坏性操作，让后面的测试全部白跑。

Fastbot 的改进可以概括为"有智能的随机"。它会读取当前界面的控件树，知道哪里是按钮、哪里是列表、哪里只是空白，并据此决定操作的权重：按钮显然比空白区域更值得点。它会记住哪些页面去过、哪些控件点过，优先探索新的地方，同样的时间能走得更深。它还支持黑名单，可以指定绝对不能碰的元素，比如"退出登录"。此外，它有一定的状态感知能力，会尽量让 App 停留在有意义的页面上，而不是陷在某个弹窗里死循环。

## 三、为什么要测 Release 包？

这是 iOS 开发容易忽略的一点。我们平时在 Xcode 里运行的是 Debug 配置，而用户从 App Store 下载的是 Release 配置，两者的差别比想象中大：

| | Debug 包 | Release 包 |
|---|---|---|
| 编译优化 | 关闭 | 开启，运行更快，崩溃栈的地址也会不同 |
| 断言与日志 | 可能有额外的断言和日志 | 部分断言被移除 |
| 内存行为 | 与线上不完全一致 | 与用户手里的一致 |
| 代码路径 | — | 某些只在 Release 下才激活的分支 |

所以，**在 Debug 包上测出来的稳定性结论，不能直接代表 Release 包的表现**。我们框架的核心原则之一，就是直接在 Release 配置的包上测试。

### 零侵入模式与 stub 模式

Fastbot 在 iOS 上有两种获取界面信息的方式，区别在于要不要动被测的 App。

**零侵入模式**完全不改 App，原样安装 Release 包，界面信息来自系统 XCTest 提供的无障碍树。它的局限是，没有实现无障碍接口的自定义控件，在这棵树里是看不见的。

**stub 模式**会在 App 进程里放一个小组件（stub）。它在 App 内部起一个轻量的 HTTP 服务，直接遍历整棵 UIView 树返回给 Fastbot，所以自定义控件也看得见。

我们很快就碰到了零侵入模式的天花板。UMU 用的是自定义的 Tab Bar，在无障碍树里完全不可见，Fastbot 无法切换 Tab，十个小时只能在第一个 Tab 的页面里打转。换成 stub 模式后，Fastbot 能自主切换 Tab，页面覆盖率明显提升。

最初的 stub 需要把源码加进 App 工程一起编译。后来我们改成了**注入**的方式：把 stub 编译成动态库，直接写进打好的 Release 包，再重新签名安装。这样既不用改 App 的源码，被测的也仍然是 Release 包本身。stub 只负责描述界面和执行操作，不涉及任何业务逻辑。注入的具体做法和踩过的坑，会在后面的工具链和覆盖率专项中展开。

## 四、Flutter 混合 App 的特殊性

UMU App 是 Flutter 混合架构：外面是原生壳（iOS 上是 Objective-C 和 Swift，Android 上是 Java 和 Kotlin），里面嵌着 Flutter 引擎，部分业务用 Dart 编写。这给稳定性测试带来了两个额外的麻烦。

### 两套崩溃体系

原生层和 Dart 层各有一套异常机制，崩溃日志的样子和还原方法都不一样：

```
原生崩溃 (ObjC/Swift)
  └── 记录在 .ips 文件
  └── 用 atos 工具 + dSYM 还原函数名

Flutter/Dart 崩溃
  └── 也记录在 .ips 文件（被包裹在原生 Crash 里）
  └── 栈帧里是 dart:: 前缀的地址
  └── 需要 flutter symbolize + 构建时的 app.dSYM 才能还原
```

如果只会处理原生崩溃，看到 Dart 层的栈帧会一头雾水：满屏的十六进制地址，没有一个函数名。

### 内存数据是合在一起的

Flutter 引擎运行在 App 自己的进程里，不是一个独立进程。所以不管用什么工具采集内存，看到的都是"原生代码 + Flutter 引擎 + Dart 堆"的总和，无法单独拆出来。

Flutter 引擎本身有 30 到 50MB 左右的固定开销，这是正常的运行成本，不是泄漏。设定内存告警阈值时要把这部分算进去，否则 App 一启动就会告警。

## 五、符号化：让崩溃日志变成人能读懂的东西

这是整个框架里技术含量最集中的部分之一，这里先建立概念。

App 打包发布时，函数名会被剥离（strip），崩溃日志里只剩下内存地址：

```
// 剥离前（开发时）
-[HomeViewController viewDidLoad] + 42

// 剥离后（发布包崩溃日志里看到的）
0x00000001042a3bc4
```

**符号化（Symbolication）就是把地址还原成函数名的过程。** 它需要两样东西。一是符号文件：iOS 上是 dSYM，Android 的 Flutter 层是 symbols 文件，它们在构建时生成，记录着地址和函数名的对应关系。二是加载基址（Load Address）：App 每次启动时被加载到内存中的位置都不同，必须用崩溃日志里记录的这个值做偏移换算，才能在符号文件里找到正确的函数。

这也是为什么我们反复强调，打包之后必须把 dSYM 归档保存。**没有 dSYM，崩溃日志就只是一堆没有意义的数字。**

## 六、ANR：Android 特有的"假死"

Android 有一类 iOS 没有的问题，叫 ANR（Application Not Responding，应用无响应）。当主线程被阻塞超过 5 秒（某些场景下是 10 秒），系统会弹出"应用无响应"对话框，问用户要不要强制关闭。

ANR 不是 Crash，进程并没有死，但对用户来说体验一样糟糕。我们的框架会从日志中识别 ANR 并单独计数，不混入崩溃数：出现 ANR 时报告判为 WARN（需要关注），但不会直接判为 FAIL。

iOS 上没有这个概念。主线程长时间卡死时，系统的看门狗（Watchdog）会直接杀掉 App，表现为一次崩溃，跳过了"无响应弹窗"这一步。

## 七、我们的框架在做什么

把前面的概念串起来，我们要搭建的这套框架，做的事情可以用一句话概括：**让 Fastbot 扮演一只不知疲倦的猴子，在真机上长时间操作 Release 包，同时把崩溃、内存和 CPU 数据都记下来，最后自动给出结论。**

拆开来看，Fastbot 负责覆盖人工无法穷举的操作序列；采集器在旁边持续记录崩溃日志和性能曲线；测试结束后，报告模块自动处理这些数据，给出 PASS、WARN 或 FAIL 的判定，失败时推送告警，不需要有人盯着。iOS 和 Android 的采集方式差别很大，但最终产出的是同一套格式的报告，方便对比和存档。

这是一套"让机器替人做粗活"的系统。它的价值不在于发现复杂的逻辑 Bug，那是代码评审和单元测试的事；而在于**通过规模化的随机操作，以很低的成本覆盖长尾的崩溃路径**。

## 八、已经有 Sentry 了，为什么还要这个框架？

这是一个很自然的疑问。答案是：**两者解决的是同一件事的不同阶段，缺一不可。**

Sentry、Firebase Crashlytics 这类平台，收集的是用户真实使用时发生的崩溃：用户崩了，日志上报，平台聚合，我们第二天打开报表才看到。这是**线上监控**，是最后一道防线。而稳定性框架是在代码发布给用户之前，就主动把问题跑出来，这是**线下预防**，是更靠前的一道防线。

测试领域把这种思路叫做**左移（Shift Left）**。如果把一个版本的生命周期画成"开发 → 构建 → 测试 → 发布 → 用户使用"，稳定性框架拦截问题的位置在"测试"这一步，而 Sentry 要到"用户使用"之后才知道出了问题。

**越靠左发现的问题，修复成本越低。** 用户已经在崩溃，意味着 Bug 在线上存活了一段时间，可能已经带来差评和投诉，工程师只能在紧急状态下修复。而由框架发现的问题，就是一个普通工作日里的任务，没有用户压力，可以从容排查。

### 两者互补，而不是替代

| | 稳定性框架（线下） | Sentry（线上） |
|---|---|---|
| **触发时机** | 上线前、每晚定时 | 用户真实使用时 |
| **操作来源** | Fastbot 模拟操作 | 真实用户的真实行为 |
| **能发现什么** | 随机操作触发的崩溃路径 | 真实场景触发的崩溃 |
| **发现不了什么** | 依赖特定账号或数据的问题 | 本该在上线前堵住的低级崩溃 |
| **修复压力** | 低，没有用户受影响 | 高，用户已经在崩溃 |

有一类问题，框架**永远发现不了**：某位用户账号下恰好有一份特殊格式的数据，触发了解析崩溃。Fastbot 用的是测试账号，没有那份数据，跑一万次也不会崩，这只能靠 Sentry 在线上捕获。

反过来，也有一类问题 Sentry **本不该有机会看到**：比如每次点"分享"必崩，这种问题理应在发布前就被框架拦下。如果框架跑了一整晚都没发现，那就是框架的问题了。

### 完整的质量防线

| 阶段 | 防线 | 做什么 |
|---|---|---|
| 开发阶段 | 代码评审、单元测试、集成测试 | 在代码层面拦住逻辑错误 |
| 上线前 | **稳定性框架**（本系列要补的这一道） | 每晚定时压测、发版前专项验证、失败自动告警 |
| 线上 | Sentry | 用户崩溃聚合上报、版本间崩溃率对比、灰度期异常监控 |

发现得越早，修复越便宜。我们已经有了 Sentry 这道最后防线，现在补的是中间这一道，两者并存，才是完整的体系。

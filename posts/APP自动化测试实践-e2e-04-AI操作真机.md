## 一、AI 操作 App，难点不在"会不会点"

让大模型操作 App，听起来只是"截个图、让模型说点哪、再点下去"。真做起来，卡住的是三件事。

第一是**看**。截图对模型是昂贵且模糊的输入：一张整屏截图编码要三千多 token，模型还得自己从像素里猜按钮的边界，再输出一个坐标——而坐标恰恰是模型最不擅长的输出。更好的输入是结构化的界面描述：有哪些可点的元素、叫什么、在哪。

第二是**动**。拿到"点第 5 个元素"之后，得有一个可靠的通道把点击送进 App，并且告诉调用方点没点成。

第三是**快**。一个探索性任务（比如"进某门课程把它收藏"）动辄十几步，每步还要一轮模型推理。如果取一次界面就要两三秒、点一次要半秒，整个任务的耗时和失败概率都会被放大到不可用。

所以问题的本质是：**怎么以足够低的延迟，拿到结构化、可信的界面描述，并把动作精确地送回去。**

## 二、业界的三条路，为什么 iOS 工具都偏爱模拟器

今年社区里冒出了一批面向 AI agent 的移动端工具，比较有代表性的是喵神的 sim-use 和 Cameron Cooke 的 AXe。它们的思路和我们高度一致：把界面压成精简文本给模型、用短序号或文案定位元素、常驻进程降延迟。但有一个共同点很显眼——**iOS 侧都只支持模拟器**，也有不少人反馈 sim-use 用不了真机。

这不是作者偷懒，是 iOS 平台决定的。模拟器本质上是 Mac 上的一个进程，宿主机可以直接调用 CoreSimulator 的私有框架读取无障碍树、注入 HID 触摸事件，设备里什么都不用装。真机就没有这个口子：iOS 沙盒不允许外部进程读别的 App 的界面，也不允许外部注入触摸。

在真机上，合法的路只剩两条：

| 路线 | 代表 | 原理 | 代价 |
|---|---|---|---|
| 模拟器 | sim-use、AXe | 宿主机调 CoreSimulator 私有 API | 只能模拟器 |
| XCTest | WebDriverAgent / Appium | 设备上跑一个开发者签名的测试进程，经系统 XCTest 通道取树和发事件 | 取树 1-3 秒、点击约 500ms，复杂页常超时 |
| 注入 | Fastbot stub、我们的方案 | 把一个动态库注入 App 进程，在进程内直接读视图树、触发控件 | 要重签名 IPA，每个版本重新注入 |

我们的稳定性测试必须跑真机——要看真实设备上的内存、CPU 和崩溃，而且不少问题只在特定系统版本的真机上出现。UMU 的包在模拟器上也不好跑（签名、Flutter 依赖都是障碍）。于是我们选了第三条路。

## 三、我们的做法：把探针放进 App 里

起点是字节开源的 Fastbot。它的 iOS 版本带了一个 stub：注入 App 后在进程内起一个 HTTP 服务，Fastbot 通过 `/view` 拿到 UIView 树，用来做智能遍历。原版 stub 只能"看"，我们在它基础上补齐了"动"的能力：点击、滚动、返回、长按、输入、截图。

```
+----------------+     HTTP :9797      +------------------------------+
|  Agent         |  -----------------> |  UMU App process             |
|  (Claude)      |   /view  /tap ...   |    FastbotStub.dylib         |
|  MCP / CLI     |  <----------------- |     - walk UIView tree       |
+----------------+     JSON tree       |     - Flutter tree via Dart  |
                                       |     - in-process touch       |
+----------------+                     |                              |
|  Fastbot       |  -----------------> |                              |
|  (XCTest)      |   /view only        |                              |
+----------------+                     +------------------------------+
```

> 同一个 stub 服务两类调用方：AI agent 经 MCP 读树并直接调动作路由；Fastbot 只读树，点击仍走 XCTest 的真实事件。

因为代码就在 App 进程里，读树不需要跨进程序列化整棵无障碍树，点击也不需要经过系统事件管道，速度差距是数量级的：

| 操作 | WebDriverAgent | stub |
|---|---|---|
| 取页面结构 | 1-3 秒 | 约 20ms |
| 点击 | 约 500ms | 约 3ms |
| 截图 | 约 800ms | 约 130ms |

拿到树之后，还要把它变成模型好用的输入。我们沿用了 AppAgent 的核心原则：**不让模型输出坐标**。代码从树里筛出可交互元素，编号、附上文案和所属页面，模型只需要回答"点哪一个"，坐标由代码计算。定位优先用文案而不是序号——列表多出一项，后面的序号就会整体漂移，按旧序号去点必然点错。

最终形态是一个 MCP server 加一份 skill：agent 自己就是主循环，看一眼、动一下、再看一眼。在真机上让 Claude 完成"进课程详情页收藏"这类任务，5 步左右即可完成并截图自证。

## 四、看得准：可点判定修正与 Flutter 并入

速度解决之后，下一个瓶颈是"看得准不准"，其中最突出的是 Flutter 页。

**Flutter 页在视图树里是一片空白。** Flutter 不使用 UIKit 控件，而是由自己的引擎把整页画在一块 FlutterView 上。所以在 UIView 树里，一个 Flutter 页面只有这一个空壳节点，下面没有任何按钮、列表或文字。UMU 有 230 个 Flutter 路由，设置页、搜索页、协同课程等都是 Flutter 实现。对 Fastbot 来说，进了这些页面就没有目标可点，只能乱点或退出，Flutter 页面覆盖率长期只有原生的一半左右。

原生手段也补不上这个缺口。Flutter 确实有一套供无障碍使用的语义树，但它默认不生成，只有系统辅助功能（如 VoiceOver）请求时才会构建。让被测 App 常开辅助功能，等于改变了被测对象本身。所以我们换了个方向：**直接问 Dart 侧要 widget 树。**

### 整体链路

```
Fastbot --POST /view--> stub (native, in App process)
                          |
                          |-- 1. walk UIView tree          -> desc (with empty FlutterView)
                          |
                          |-- 2. MethodChannel "getTree"   -> Dart: ui_tree_spy
                          |        timeout 0.3s                 returns JSON nodes
                          |
                          |-- 3. filter nodes, attach as children of FlutterView
                          v
                       merged desc --> Fastbot (tap via XCTest at node center)
```

> 第 2 步失败或超时就跳过第 3 步，原样返回第 1 步的树，所以最坏也只是退化成改造前的效果。

### 第一步：stub 怎么跟 Dart 说话

Flutter 嵌在原生 App 里时，原生和 Dart 之间的标准通信方式是 MethodChannel：原生侧按通道名调用一个方法，Dart 侧注册同名通道的处理函数并返回结果。UMU 的 Flutter 模块里加了一段 `ui_tree_spy` 代码，在 `umu.flutter.module/uitree` 通道上响应 `getTree` 方法：遍历当前页面的 widget 树，返回一个 JSON 节点列表。每个节点带有 widget 类型、屏幕上的矩形、是否可点、是否可滚动、文字内容、标识和树中深度。

stub 这边要做三件事。先从各个窗口出发沿视图层级和响应链找到当前的 FlutterViewController，再取它的 `binaryMessenger`（引擎的消息通道），最后用通道名建一个 FlutterMethodChannel 发起调用。

这里有一个刻意的设计：stub **不链接 Flutter.framework**，所有 Flutter 相关的类和方法都在运行时按名字查找、动态调用。这样同一个 stub 可以注入任何 App，纯原生 App 里查不到 Flutter 类就直接返回"不支持"，不会因为缺少依赖而加载失败。

### 第二步：超时与降级

MethodChannel 是异步的，而且有一个坑：如果 Dart 侧根本没注册这个通道（比如 App 是没带 `ui_tree_spy` 的旧版本），回调**永远不会来**，不报错，也不超时。stub 若干等，Fastbot 的那次 HTTP 请求就会一直挂着。

所以每次调用都配了超时兜底。Fastbot 每做一个动作都会请求一次 `/view`，这里只给 0.3 秒；单独给管理后台和 agent 用的 `/fluttertree` 路由给 3 秒。当前页面不是 Flutter 页时，stub 直接同步返回，不产生任何等待。无论超时、通道缺失还是返回内容解析失败，`/view` 都原样返回 UIView 树。也就是说，这个能力只会加分，不会让原生页面变差。

### 第三步：过滤节点，挂进原生树

Dart 返回的是完整的 widget 树，节点数量多，而且大量是布局用的壳子。直接塞给 Fastbot 只会制造噪音。我们按下面的规则筛选，这套规则与管理后台设备镜像画 Flutter 线框时用的完全一致：

| 规则 | 原因 |
|---|---|
| 只保留可点或可滚动的节点 | 纯布局、纯装饰的 widget 对遍历没有意义 |
| 矩形完全相同的节点只留最外层 | Flutter 里点击组件常常层层嵌套（如 InkResponse 套 GestureDetector），矩形完全重合，留一个就够 |
| 丢掉完全在屏幕外的节点 | 列表里还没滚到的项，点了也点不到 |
| 丢掉贴着屏幕顶部、满宽、高度不超过 120 且没有任何文字的节点 | 这是 Flutter 页面常见的"吞手势"顶栏，覆盖整条导航区但本身不是可操作目标 |
| 把节点范围内的文字挂成它的标签（最多两段） | 让"可点区域"带上人能读懂的名字，日志和报告里能看出点的是什么 |

筛完的节点作为**虚拟子节点**挂到 UIView 树中的 FlutterView 下面，类型记为 `Flutter.<Widget 类型>`，标记为可见、可交互。如果树里有多个 FlutterView（FlutterBoost 多容器时，栈底的页面也还在树里），就挂到按遍历顺序最后一个可见的上面，它是最上层、用户正在看的那一个。

为什么不单独给 Fastbot 开一个 Flutter 路由，而要挂进 `/view`？因为 Fastbot 的 Runner 是闭源的，只会请求 `/view` 并按固定结构解析。把 Flutter 节点伪装成普通子视图，是不改 Fastbot 就能让它"看见" Flutter 的唯一办法。Fastbot 拿到这些节点后，和对待原生控件一样，取矩形中心点，通过 XCTest 发真实的触摸事件。真实事件会正常进入 Flutter 引擎的手势系统，所以点得到。

实测搜索页能并入 12 个可点节点和 3 个可滚动节点，一次 `/view` 往返约 155ms（经 Wi-Fi 测量，包含 Dart 侧遍历的时间）。

### 已知局限

- **App 必须带 `ui_tree_spy`。** 这段 Dart 代码要放进 App 仓库，需要 Flutter 开发同事配合，并且要跟着版本一起发布。目前只有我们的测试包带了它。
- **坐标直接当屏幕坐标用。** Dart 侧给出的是 Flutter 视图内的逻辑坐标，stub 没有再换算到屏幕坐标。UMU 的 Flutter 页目前都是全屏的，两者一致；如果以后出现 FlutterView 不在屏幕原点的嵌入式页面，坐标会有偏差，需要再做一次换算。
- **agent 侧仍然点不进去。** stub 自己的点击是在进程内直接调用控件的 target/action，不走系统事件分发。Flutter 内部没有原生控件可调，所以 agent 能"看见"这些节点，却点不着。Fastbot 不受影响，因为它的点击走 XCTest。这是注入方案目前最大的能力边界，要补上需要在 App 内合成真实触摸事件，或者对 Flutter 页退回 Appium。

两项修正合称 C 组。目前只有一晚干净的数据，但幅度很明显：

| 分组 | 时间 | 原生页面覆盖 | Flutter 页面覆盖 | 总覆盖 |
|---|---|---|---|---|
| B 组（增强树） | 09-22 ~ 10-04，13 晚 | 13.6% ~ 20.1% | 6.1% ~ 11.5% | 10.8% ~ 16.2% |
| C 组（可点修正 + Flutter） | 10-08，1 晚 | 35.5% | 18.7% | 27.9% |

> 覆盖率口径：双账号各跑 5 小时后取页面并集；分母为包内静态扫描出的 279 个原生页面和 230 个 Flutter 路由。C 组样本量还不够，需要继续观察。

## 五、未来的规划和优化方向

回到开头说的"看、动、快"，目前三件事都还没有做到头，接下来的工作也沿着这三条线展开。

### 先补上最大的缺口：让 Flutter 页点得着

第四节解决了 Flutter 页"看得见"的问题，但 agent 仍然点不进去。原因在于 stub 的点击是在 App 进程内直接调用控件的响应方法，绕开了系统的事件分发，而 Flutter 内部根本没有原生控件可供调用。要真正点进去，可以在 App 进程内合成真实的触摸事件，让每一次点击都像手指按下一样走完整条系统事件链路。这样做的好处是一劳永逸，Flutter、WebView，以及自己重写了触摸处理的自定义控件都能一并覆盖，缺点是实现门槛较高。另一条路是遇到自绘页面时退回 Appium，现成可用，但要用速度去换覆盖。比较现实的形态，大概是先用后者兜底，再逐步用前者替换。

### 让 agent 看得更准

设备镜像里还能看到一些"双层框"：外层容器和里面的按钮同时被识别成了可点元素。它们会挤占候选列表，也会让模型在两个几乎重合的选项之间犹豫，所以判定规则还需要继续收敛。

更棘手的是没有文案的图标按钮。课程详情页右上角的收藏、分享、更多，在树里只有类型和尺寸，模型只能凭序号去猜。我们打算在遇到这类无名图标时，自动裁剪出那一小块截图交给视觉模型辨认，再按位置把结果缓存下来，同一个图标只问一次。裁剪后的图片只有几 KB，成本足够低，可以常态化使用。

此外，sim-use 的一个小设计也值得借鉴：把元素按屏幕区域分成顶部导航、内容区和底部栏三段输出。这几乎不增加成本，却能让模型一眼建立起页面的大致结构。

### 让 agent 少走冤枉路

现在 agent 有相当一部分步骤花在了"确认"上：页面还没加载完就去看，看到了再看一遍，点完了不知道生效没有，又看一遍。这些来回都可以省掉。

第一步是让点击支持"等到目标出现再执行"。stub 取一次树只要 20ms，在设备侧轮询几乎没有成本，比让 agent 自己反复查看高效得多。第二步是保证每次界面描述的输出顺序稳定，这样动作之后只需要返回新增和消失的元素，既节省 token，也直接回答了"刚才那一下有没有生效"。再往前一步，像登录、填写表单这类固定流程，完全可以一次调用连续执行多步、遇错即停，不必每一步都请模型参与。

### 让定位更稳

目前 agent 优先按文案定位，比按序号可靠得多，但文案本身也会变：课程名来自用户数据，按钮文字可能随版本或语言调整。对探索任务来说这问题不大，对需要长期回放的 E2E 用例就很致命。

一个改进方向是识别页面里的主列表，允许直接说"点第 3 行"，用结构代替具体内容。更根本的办法，是推动 iOS 和 Flutter 开发给关键控件加上稳定的无障碍标识（accessibilityIdentifier），让定位彻底摆脱文案和位置的变化。这需要和开发团队一起推进，会是一项长期工作。

### 工程上的两件基础工作

最后还有两件不显眼、但应该尽早做的事情。一是 stub 的版本与健康自检：调用方在开始操作前，先确认设备上的 stub 版本是否匹配、取树是否正常，出问题时立刻报错，而不是悄悄降级、让上层在错误的数据上继续跑。二是默认安全：stub 目前监听所有网卡且没有鉴权，同一局域网内的任何人都能操作这台设备上的 App。更合理的默认值是只监听 USB 连接，并在启动时下发一个随机口令，每个请求都要校验。

---

## 结语

回头看，注入式 stub 的价值在于把"AI 操作真机"的单步成本从秒级压到了毫秒级，让探索性任务从不可用变成可用；它的代价是要维护一个活在被测 App 进程里的组件，这个组件的任何 bug 都会被放大成测试结果的失真。C 组的可点修正和 Flutter 并入则说明，"看得准"带来的收益可能比"看得快"更大。

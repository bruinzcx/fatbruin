## 一、报告模块：唯一的跨平台汇聚点

回顾整个框架的数据流，iOS 和 Android 的采集方式几乎没有一处相同，但它们最终都汇入同一个出口：

```
iOS 采集                       Android 采集
  perf_raw.jsonl  ──┐            perf_raw.jsonl  ──┐
  crashes.jsonl   ──┤            crashes.jsonl   ──┤
  coverage.json   ──┤            coverage.json   ──┤
                    v                              v
              reporter.py（两端共用）
                    │
       report.json · report.html · Slack 告警
```

两端的采集脚本在写文件时就把格式统一了：`perf_raw.jsonl` 每行是一个时间点的性能快照，`crashes.jsonl` 每行是一条崩溃记录，`coverage.json` 记录本次访问过的页面。报告模块只认这三个文件，不关心数据是怎么来的。

这个设计的好处是，**将来接入一个新平台（比如鸿蒙），只需要写新平台的采集脚本，报告部分一行都不用改。** 报告的判定逻辑、HTML 模板、告警推送也因此只维护一份，两端的报告长得一模一样，方便对比。

## 二、内存：看水位，更要看趋势

报告模块读取全部内存采样点，先算出几个基本指标：均值、峰值和 P95。

为什么在峰值之外还要看 P95？因为峰值很容易被一次瞬间的毛刺拉高，比如加载一张大图的那一刹那，它不代表 App 长期处在这个水位。P95 去掉了最高的 5% 采样点，回答的是"除了偶发的极端情况，App 的内存高水位大概在哪"，更能代表用户的真实体验。

### 泄漏要看趋势

内存泄漏不能靠峰值判断，要看**趋势**。我们的做法很朴素：比较测试后 20% 时间段的内存均值和前 20% 的均值，差值超过 50MB 就标记为"疑似泄漏"。

正常的 App 内存会随着页面进出起起落落，但总体围绕一条基线波动；泄漏的 App 则是一路上涨、从不回落。前后两段均值一比，趋势就出来了。

需要说明的是，"疑似泄漏"目前只在报告里展示，**不参与判定**。Monkey 测试的操作路径是随机的，后半段恰好走进了图片、视频密集的页面，均值自然会高，单凭这一个信号直接判 WARN 会产生太多误报。它更适合作为人工复查时的线索。

### OOM 风险与设备档位

判定看的是峰值。我们按设备的物理内存大小分了几个档位，每档设置不同的警戒线：

| 设备内存 | 峰值超过此值判 WARN |
|---|---|
| 4GB | 1200MB |
| 6GB | 1500MB |
| 8GB | 2000MB |

此外，如果峰值超过设备总内存的 70%，就认为有被系统强杀的风险，直接判 FAIL。

设备的总内存无法通过命令动态查询，所以每台测试设备在注册时都必须手动填写这个值（查设备规格表），否则报告无法计算 OOM 阈值。

### 数据本身可不可信

还有一种情况容易被忽略：采集本身出了问题。比如性能采集进程中途挂掉，或者长时间挂载不上，结果整份报告的内存数据只有寥寥几个点，算出来的峰值低得漂亮，报告却静默地判了 PASS。

为此，报告模块会读取采集器记录的"采集覆盖度"：实际采到数据的时长占计划时长的比例。低于 80% 时，认为内存数据不可信，判为 WARN；内存数据完全为空时也一样。**宁可让人看一眼，也不能让数据丢失伪装成一切正常。**

## 三、CPU：只展示，不判定

CPU 使用率同样会计算均值和 P95，并在报告里画出折线图，但它不参与判定。

原因在于 Monkey 场景下的 CPU 高低很难定义"正常"：Fastbot 每 300 毫秒就操作一次，App 一直在加载页面、渲染列表，CPU 本来就不会低；不同页面之间差异也很大。在没有稳定基线之前强行设阈值，只会制造噪音。CPU 数据目前主要用于人工排查和版本间的对比。

FPS 两端目前都没有采集，阈值配置里虽然预留了卡顿和冻屏的参数，但还没有启用。

## 四、崩溃：去重之后才有信息量

### 指纹去重

同一个 Bug 在几个小时的测试里可能被触发几十次。如果报告只说"崩溃了 30 次"，读者无法判断这是一个问题反复出现，还是 30 个不同的问题。

所以每条崩溃记录都会生成一个**指纹**：由异常类型加崩溃线程最顶层的函数组成，比如 `EXC_BAD_ACCESS|-[XXXViewController dealloc]`。指纹相同就视为同一个问题。报告展示的是"**N 种崩溃，共触发 M 次**"，这比单纯的次数有信息量得多：1 种崩溃触发 100 次，和 100 种崩溃各触发 1 次，是完全不同的严重程度。

iOS 上，系统因内存过高强杀 App 时会留下 Jetsam 记录，这类事件同样会被识别出来，归入单独的指纹。

### 判定：零容忍，但要分清是谁的错

崩溃的判定规则很简单：只要出现一次 App 自身的崩溃，就判 FAIL。内存有"勉强可接受"的灰色地带，崩溃没有，用户体验是零容忍的。

但"App 自身"这几个字很重要。长期运行下来，我们发现有两类"崩溃"并不是 App 的问题：一类是测试工具（注入的 stub）自己引起的崩溃，另一类是 Android 上的 ANR。它们都单独计数，只判 WARN，不判 FAIL。如果不做这层区分，测试工具的 Bug 会被当成 App 的 Bug 报出去，整套告警的可信度也就没了。

### 总体结论

最终结论取各项中最严重的那个：任何一项 FAIL，整体就是 FAIL；没有 FAIL 但有 WARN，整体就是 WARN；全部通过才是 PASS。参与判定的是内存水位、内存数据可信度、崩溃、ANR 这四项。

## 五、报告长什么样

每次运行产出两份文件。

**`report.json` 给机器读。** 它包含结论、各项指标和元信息，管理后台、批次汇总、告警推送都从这里取数据：

```json
{
  "result": "WARN",
  "meta": { "device": { "model": "iPhone 14 Pro Max", "total_ram_mb": 6144 }, "duration": 18000, "account": "bruin" },
  "memory": { "avg_mb": 318.4, "peak_mb": 681.7, "p95_mb": 512.0, "growth_mb": 37.3, "leak_suspected": false, "oom_risk": false, "status": "PASS", "completeness": 0.97 },
  "cpu": { "cpu_avg": 12.1, "cpu_p95": 24.3 },
  "crash": { "total_count": 0, "unique_count": 0, "anr_count": 0, "stub_crash_count": 1, "status": "WARN" },
  "coverage": { "native_rate": 35.5, "flutter_rate": 18.7, "overall_rate": 27.9 }
}
```

写这个文件时用的是"先写临时文件再改名"的原子写法：长时间任务随时可能被中断，绝不能留下一份写了一半的 JSON，让下游读到半截数据。

**`report.html` 给人读。** 打开就能看到结论徽章、内存和 CPU 的趋势折线图、崩溃列表（附可下载的原始崩溃日志）以及访问过的页面清单。

折线图有一个细节值得一提。5 小时的长跑单账号就有上万个采样点，全部画出来，线又密又抖，真正重要的峰值反而淹没在噪声里。我们在渲染前用 LTTB 算法把点抽稀到 300 个左右。它和滑动平均不同，挑代表点时会专门保留极值，所以内存峰值和 CPU 尖峰不会被抹平。在稳定性报告里，峰值本身就是信号。

## 六、页面覆盖率：一个指标引出的专项

前面的指标回答的是"App 稳不稳"。但还有一个问题同样重要：**测试到底测到了多少？** 如果 Fastbot 跑了 10 个小时都在同一个页面里打转，报告再干净也说明不了什么。页面覆盖率就是回答这个问题的：访问过的业务页面数，除以 App 里的业务页面总数。

分母来自对安装包的静态扫描（见第二、三篇），分子来自测试过程中记录的页面访问日志。覆盖率会在报告里展示，但**不参与总判定**：短时任务或单账号任务的覆盖率天然偏低，用它卡结论并不公平。

### 起点：10 小时只有 13%

第一次认真看这个数字时，我们吓了一跳：iOS 一轮 10 小时的遍历，总覆盖率只有 13.3%，其中原生页面 17.7%，Flutter 页面只有 7.9%。可同一轮里，Fastbot 走出了 1596 个不同的界面状态，执行了 9395 次操作，它显然没有卡住不动。低覆盖不是"跑得不够"，而是结构性的问题。

最初的两个猜测都被实测推翻了。一是怀疑探索深度设得太浅，但日志显示新页面一直在零星增加，深层页面也能到达，只是到得慢。二是怀疑底部的 Tab 按钮看不见，但真机上逐个检查，五个 Tab 都能看见、都能点。

### 根因一：时间分配严重不均

把 10 小时里的所有点击按底部 Tab 归类，问题一目了然：

| Tab | Fastbot 点击次数 | 探索情况 |
|-----|-----------------|----------|
| 课程（最左） | 888 | 充分 |
| 首页 | 约 0 | 几乎没进 |
| 个人中心 | 约 0 | 几乎没进 |
| 我的工作台 | 约 0 | 几乎没进 |
| 部门看板（最右） | 895 | 充分 |

Fastbot 的探索策略天然偏爱能不断产出新状态的"大子树"。App 启动后落在课程 Tab，它一头扎进课程和部门看板这两棵最深最富的子树，就再也出不来了，中间三个 Tab 的整块业务从头到尾几乎没碰过。问题不在于点不到，而在于有限的时间没有被摊开。

### 根因二：Flutter 页面不透明

点击热点里有一个覆盖整个屏幕的元素，被点了整整 2854 次，占全部点击的三分之一。这正是 Flutter 页面在 Fastbot 眼里的样子：整页坍缩成一个大块，里面几十个按钮、列表一个都看不见。Fastbot 点几次发现没收获，就会降低它的权重、彻底放弃，因为里面的控件自始至终就没有可点的入口。这是给再多时间也解决不了的硬天花板。

### 解法一：多账号分区采集

针对时间分配不均，我们借助了 UMU 的一个现成特性：底部 Tab 的显示与隐藏，由后台按账号配置。只要登录不同的账号，Fastbot 能看到的 Tab 就不同，它会被"天然聚焦"在这个账号可见的几个 Tab 上，Fastbot 本身一行代码都不用改。

难点在于登录。Fastbot 是随机操作，不可能输对账号密码。我们的做法是在注入的 stub 里加一个"自动登录"能力：App 启动时，如果启动参数里带了登录令牌，stub 就调用 App 自带的令牌登录接口静默完成登录；换账号时先清掉旧的登录态。这段逻辑只存在于注入了 stub 的测试包里，正式包没有，不会外泄。令牌只保存在本机的配置文件里，不进代码仓库，也不写进任何报告。

这里还踩过一个坑：传给 App 的多个启动参数要用冒号分隔，一开始误用了空格，登录参数被并进了端口参数里，从未生效。偏偏端口参数取整数时仍能解析出正确的端口，服务照常启动，把失败完全掩盖了。

实际运行时，夜间任务会依次用两个专用测试账号各跑 5 小时。专用账号很重要：Fastbot 会随机创建、修改、删除数据，绝不能用真人账号或共享账号去跑。

### 解法二：并集聚合

多个账号各自跑完后，单看每一份报告，覆盖率都不高。必须把它们访问过的页面**求并集**，再对同一个分母计算，才是这一轮测试真实的总覆盖。

我们用目录结构本身来表达"批次"：一次多账号运行就是一个批次文件夹，每个账号各占一个子目录，存放自己的完整报告；全部跑完后，汇总脚本扫描这些子目录，把访问过的页面按原生和 Flutter 分别去重求并集，生成批次级的汇总数据和一份富报告。汇总报告复用了单次报告的同一个模板，内存曲线也会把各账号的数据拼成一条连续的长线。同时还会算出每个账号的"独占贡献"，也就是只有它到过、其他账号都没到过的页面数，用来评估每个账号的 Tab 配置是否合理。

第一晚的实测结果验证了这个思路：

| | 账号 A 单跑 | 账号 B 单跑 | **并集** |
|---|---|---|---|
| 总覆盖率 | 14.3% | 12.2% | **21.4%** |
| 独占页面数 | 47 | 36 | — |

两个账号各自的覆盖率和过去单账号的水平差不多，但并集一下跳到了 21.4%。两个账号各自独占了几十个对方到不了的页面，说明分区确实把探索时间摊开了。

### 解法三：让 Flutter 页面可见

Flutter 的天花板，靠调度是解决不了的。我们后来从 Dart 侧补了一条通道，把 Flutter 页面里可点、可滚动的节点作为虚拟子节点交给 Fastbot，同时修正了 stub 里一处可点判定的坐标换算错误。这组改动上线后的第一晚，总覆盖率达到 27.9%，其中 Flutter 页面从 8% 左右提升到 18.7%。具体做法在 E2E 系列第四篇《让 AI 直接操作真机 App》中有详细说明。

回头看，覆盖率从 13% 到 28% 的提升，没有一项来自"让 Fastbot 更聪明"，而都来自"让它看得见、让它的时间花得更均匀"。

## 七、让测试每晚自动跑起来

### 一条命令，全自动

整个框架的入口只有一个：

```bash
python3 project/stability/iOS/src/run.py --config <运行配置>
```

运行配置里声明了设备、被测包、时长、要用哪些账号。主控脚本据此安装测试包、启动 Fastbot 和各个采集器、逐个账号运行、最后生成报告和批次汇总，全程不需要人参与。

### 为什么不用云端 CI

最初的设计是接入 GitHub Actions 这类 CI 流水线。但 iOS 测试必须在 USB 连接的真机上跑，云端的 Linux 主机连不了设备，只能用一台实体 Mac 作为自托管的执行机。既然无论如何都需要这台常驻的 Mac，最终我们选择了更简单直接的方式：在一台 Mac mini 上用 macOS 自带的定时任务（launchd）每晚 23:00 触发，iOS 和 Android 测试机都连在这台机器上。

### 结论怎么送到人手里

测试跑完，结论有三个去处。

第一个是 **Slack 告警**。只有结果为 FAIL 时才推送，并 @ 频道里的所有人；PASS 和 WARN 都保持静默。这是刻意的取舍：如果每晚都推一条消息，大家很快就会习惯性忽略，等真正出问题时反而没人看。

第二个是**报告索引页**。每次运行结束都会刷新一个汇总页面，按日期列出所有历史运行，多账号批次折叠成一行，展示并集覆盖率，点开可以看各账号的单独报告。

第三个是**管理后台**。它部署在内网，QA 同事可以在网页上查看报告、发起任务、管理设备和测试账号，不再需要登录那台 Mac 敲命令。管理后台的设计思路，会在管理后台系列中单独介绍。

## 八、这一篇的核心结论

| 问题 | 答案 |
|------|------|
| 报告模块为什么能跨平台？ | 两端采集脚本统一了中间文件的格式，报告只认格式，不认平台 |
| P95 比峰值好在哪？ | 去掉瞬间毛刺，反映持续的高水位 |
| 疑似泄漏为什么不参与判定？ | 随机操作的路径差异会造成大量误报，目前作为人工复查线索 |
| 采集出问题怎么办？ | 采集覆盖度低于 80% 或内存数据为空时判 WARN，不让数据丢失伪装成 PASS |
| 崩溃为什么没有 WARN 档？ | App 自身的崩溃零容忍；测试工具引起的崩溃和 ANR 单独计数，只判 WARN |
| 覆盖率为什么一开始只有 13%？ | 探索时间集中在两个 Tab，加上 Flutter 页面在 Fastbot 眼里是一整块 |
| 覆盖率是怎么提上来的？ | 多账号分区摊开时间，并集聚合正确度量，Flutter 节点并入破除天花板 |
| 为什么没用云端 CI？ | 真机必须 USB 连接，最终用一台常驻 Mac mini 定时运行 |
| 为什么只在 FAIL 时告警？ | 告警太频繁会被习惯性忽略 |

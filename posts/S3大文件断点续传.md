## 需求由来

日本客户反馈：网络不好时上传 AI 作业视频耗时极长，常见「进度条走了一大半后长时间卡住 → 只能杀 APP 重传」。诉求是上传失败后接着上次进度继续。

日本站点文件存储用 AWS，iOS 端已接入 AWS S3 SDK。改造方向：**单文件上传 → 支持断点续传的分片上传**。

## 两个前提

断点续传成立的前提只有一条本质要求：**本地文件与云端文件一对一映射**。

拆开是两个条件：
1. 文件一致
2. bucket 信息与上传地址一致

业务逻辑必须能判断"不同的上传请求负载是不是同一个文件"；确认是同一个文件后，从缓存取出**上次用的 bucket 和 path** 初始化 SDK，继续未完成的任务。

**文件唯一标识不能用文件 Path 的 MD5**——文件在多次任务间可能被改动，Path 不变而内容变了，续传会拼出残缺文件。正确做法是**对文件内容本身做哈希校验**。

本地缓存视项目情况选数据库或直接 `NSUserDefaults`。

## 分片上传的生命周期

本质是本地维护一个多分片上传任务的生命周期：

1. 开始分片上传任务 → 返回一个 upload id
2. 本地记录每个分片的上传结果
3. 全部完成 → 调合并分片接口
4. 中途失败 → 下次启动时跳过已完成分片（严格说应以**服务端查询到的已完成分片**为准，本地记录是简化理解）

## 两个坑

### 坑 1：分片一致性

分片不一致的后果分级：**缺分片 → 内容丢失；顺序或内容错 → 视频跳帧/黑屏，极大概率转码失败**。合并后才暴露，代价高。

另外大文件切分片本身消耗大、耗时长，**不应该每次开始上传都重新切**。

移动端解法是文件沙盒 + 缓存：

- **物理分片**：拿到新任务先切片，分片文件缓存本地并配任务 id；下次匹配到相同 id 直接取缓存分片上传。
- **逻辑分片**（更优）：只要确定是同一个文件，**只保存每个分片的 range**，上传时按 range 读取对应数据段。首次分片的时间开销也一并省掉。

### 坑 2：状态管理（后台 / 杀 APP）

iOS 靠 `NSURLSession` 的 **Background Session** 模式把上传任务交给系统：

- 通过 `URLSessionConfiguration.background(withIdentifier:)` 创建的任务，App 不运行甚至已终止时仍可执行。
- App 被挂起/终止时系统接管；网络恢复后系统尝试继续；任务完成时唤醒 App 处理。

这是系统级、比任何应用层重试都更强的自动恢复机制。

单分片失败的重试策略见仁见智，一般用指数回退。

## 落地实现

**核心只有一句话**：SDK 在初始化 `AWSS3TransferUtility` 时会自动恢复未完成的任务。重复调上传业务时，**取出未完成任务，重新赋值进度回调和结果回调即可**——不要重建任务。

### 必须挂的 AppDelegate 回调

想让 Background Session 正常记录每个后台分片任务的完成状态，这个回调是硬前提：

```objectivec
- (void)application:(UIApplication *)application
    handleEventsForBackgroundURLSession:(NSString *)identifier
                      completionHandler:(void (^)(void))completionHandler {
    [AWSS3TransferUtility interceptApplication:application
          handleEventsForBackgroundURLSession:identifier
                            completionHandler:completionHandler];
}
```

### 关键配置

```objectivec
AWSS3TransferUtilityConfiguration *transferConfig = [[AWSS3TransferUtilityConfiguration alloc] init];
transferConfig.accelerateModeEnabled = NO;
transferConfig.retryLimit = 1;
transferConfig.multiPartConcurrencyLimit = @(5);          // 并发分片数，控制带宽占用
transferConfig.timeoutIntervalForResource = 60 * 60 * 2;  // 120 分钟
```

注册必须走 `completionHandler` 异步等待内部数据库等操作完成后再取实例——**官方推荐用法**：

```objectivec
[AWSS3TransferUtility registerS3TransferUtilityWithConfiguration:configuration
                                    transferUtilityConfiguration:transferConfig
                                                          forKey:configKey
                                               completionHandler:^(NSError * _Nullable error) {
    AWSS3TransferUtility *s3 = [AWSS3TransferUtility S3TransferUtilityForKey:configKey];
    // ...
}];
```

### 提取未完成任务（最容易踩的地方）

```objectivec
// 注意：这是异步任务，必须用 continueWithSuccessBlock 回调。
// SDK 对同步/异步任务标识不清，很容易掉进去。
[[s3 getMultiPartUploadTasks] continueWithSuccessBlock:^id(AWSTask<NSArray<AWSS3TransferUtilityMultiPartUploadTask *> *> *t) {
    AWSS3TransferUtilityMultiPartUploadTask *progressTask;
    for (AWSS3TransferUtilityMultiPartUploadTask *task in t.result) {
        if ([task.key isEqualToString:self.context.path]) {   // key 即云端文件 path
            progressTask = task;
        } else {
            [task suspend];   // 其他任务只暂停，不要 cancel —— cancel 会丢进度
        }
    }
    fulfill(progressTask);
    return nil;
}];
```

拿到匹配任务后**直接设回调 + resume，不要重建**：

```objectivec
if (progressTask
    && progressTask.status != AWSS3TransferUtilityTransferStatusError
    && progressTask.status != AWSS3TransferUtilityTransferStatusCancelled) {
    [progressTask setProgressBlock:uploadTaskProgressBlock];
    [progressTask setCompletionHandler:uploadTaskCompletionBlock];
    [progressTask resume];
} else {
    // 走新建分支。注意：SDK 内部即使是相同文件也会重新创建新任务，比较坑
    [self.transferUtility uploadFileUsingMultiPart:... ];
}
```

## 网络抖动导致的「弱网假死」

分片上传等待时间长，`timeoutIntervalForResource` 一般设得很大。而 SDK 内部开了 Background Session 会自动处理断网恢复——**断网时不会回调任务失败**。

对有前台进度展示的业务，后果是：断网了，既不报错、进度也不动，**用户被无限等待锁死在上传界面**。

**处理原则**：
- 业务层自行检测断网或其他业务报错，**解锁 UI 反馈**，让用户有机会去做别的事。
- **只做业务层回调，不要手动显式暂停或取消任务**——`NSURLSession` 会自己处理。不必关心上传时机，只接收结果。
- 全局维护上传成功状态：用户重复上传相同文件（且两个前提一致）且已检测到成功，直接回调成功——**"秒传"**，体验提升明显。

## 思考

**关于 AWSS3TransferUtility**：API 很封闭，很多想手工介入的地方要么没接口要么没效果。且大量方法不标注同步/异步，有些明明是异步处理却不在参数里给结果回调，必须靠额外封装的 `AWSTask` 处理。

**但结论是正向的**：SDK 内部做得比较完善，业务层不必要手工介入，只负责处理过程和结果回调即可。

**更普适的一条**：这套断点续传的效果绝大部分依赖系统 `NSURLSession` 的能力特性。做网络请求相关的优化或基建时，**先研究官方系统提供的能力**——不论谁家的 SDK，只要还在 APP 应用层，最终都必须调底层 API 才能实现功能。

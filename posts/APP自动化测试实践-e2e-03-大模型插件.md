> 本文是系列《AI背景下的APP端自动化测试实践》E2E 自动化部分的第三篇。
>
> 上一篇的结论是选择 Appium：它能测真实的 Release 包、能在 iOS 真机上跑、能覆盖原生、Flutter 和 H5 三个世界。但它也有一个老问题：脚本难写、难维护。这一篇讲我们怎么用大模型来补这块短板，把录制、生成、回放、自愈串成一个 QA 能直接上手的 Claude Code 插件；以及在这个过程中，为了让 AI 操作得更快，我们探索出的另一条路——绕开 Appium，直接驱动 App。

---

## 一、裸写 Appium 脚本，苦在哪里

Appium 选对了，但直接交给 QA 同事用，门槛并不低。要懂定位策略，知道什么时候用标识、什么时候用文本；要手写等待，处理页面加载和动画；界面一改版，定位失效，脚本就成片地断；失败了，只能对着一行 `element not found` 干瞪眼，不知道当时屏幕上是什么。

这些恰恰是大模型擅长的事情：看懂界面、理解意图、判断"这一步是不是做对了"。所以我们的目标很明确：**让 QA 用自然语言描述意图，由大模型借助 Appium 生成脚本；回放时快速给出结果；脚本因界面变化失效时，由大模型给出修复建议，交给人审核。** QA 不需要了解 Appium 的任何内部细节。

---

## 二、整体流水线：录制、生成、回放、自愈

整套方案是一条流水线，交付形态是一个 Claude Code 插件，QA 通过几个斜杠命令使用：

```
/ios-case-record   QA 在真机上操作一遍，工具自动抓取每一步的界面
        |
        v
/ios-case-build    大模型分析录制产物，推断操作步骤，在真机上逐步验证
        |          产出可回放的用例（journey），验证通过后再固化成确定性脚本
        v
/ios-case-replay   回放用例，产出带每步截图的报告
        |
        v
/ios-case-heal     回放失败时，重新观察现场，判断原因，给出修复建议供人审核
```

另外还有一个 `/ios-e2e-setup`，负责检查 Appium、设备、签名等环境，并交互式地生成配置文件。环境问题是 E2E 最常见的拦路虎，把它做成一个单独的入口，能省下大量排查时间。

大模型接入设备，用的是 Appium 官方的 MCP 服务（Model Context Protocol，一种让大模型调用外部工具的标准协议）。它把读取页面结构、截图、查找元素、点击、输入这些能力直接暴露给 Claude Code，不需要我们自己造轮子。

## 三、录制：让 QA 先操作一遍

最初的设想是让 QA 用自然语言描述任务，由大模型自己摸索着在 App 里完成。后来发现，让 QA 直接在真机上操作一遍，效率和准确度都高得多：人知道该怎么走，大模型只需要"看懂人做了什么"。

录制工具在 QA 操作期间持续轮询，抓取屏幕截图和页面结构，并自动检测"转场"：页面结构发生明显变化的时刻，就是一次操作生效的时刻。录制结束后，产物是一组截图、页面结构快照，以及检测到的转场列表。

接下来由大模型逐个分析转场：对比前后两帧，推断"这一步是点了哪个按钮、输入了什么"，再通过 Appium MCP 在真机上实际执行一遍，确认定位真的能找到元素、操作真的能产生预期的效果。验证通过的步骤，连同断言一起写成一份用例文件（journey）。

第一条验证用例是 Chatbot 练习流程：录制得到 25 帧，检测到 4 次转场，大模型推断出 5 步操作；之后无人值守回放 5 步全部通过，总耗时约 18 秒。

## 四、回放：两种模式，按用例性质分派

回放是整个方案里最需要想清楚的环节。录制和自愈一定要有大模型参与，分歧只在回放。

### 为什么不能全用大模型

如果每次回放都让大模型来操作，看起来最智能，实际上有三个问题。一是**贵和慢**：每跑一次都要消耗 token。二是**不可复现**：同一条用例，今天和明天的执行路径可能不一样。三是最根本的一条：**一个既"开车"又"判分"的大模型，会把本该抓住的回归悄悄绕过去。** 按钮挪了位置，它会自己找到新位置点下去，然后报告"通过"，可这恰恰可能就是一个需要被发现的变化。

### 为什么也不能全用固定脚本

反过来，有些用例天生是模糊的。比如 Chatbot 的多轮对话：AI 每次的回答都不一样，"回答是否切题"这种判断，固定的断言根本写不出来。

### 双模回放

所以我们按用例的性质分成两种模式。

**确定性回放**是默认模式。已经验证通过的用例，会被固化成一个纯 Python 脚本，由回放引擎直接通过 Appium 执行，完全不调用大模型，零 token、速度快、结果可复现。它只有一层 5 秒的隐式等待来兜住界面抖动，找不到元素就判失败，回放期间绝不自作主张换定位、改断言。

**大模型主导回放**用于处理模糊或语义类的用例。用例脚本被当作"软计划"，由 Claude Code 经 Appium MCP 执行，并由大模型现场判定结果。为了防止它绕过回归，执行它的 skill 设有明确的门禁：它的角色是"**忠实执行、判定结果、上报偏离**"，而不是"想办法让用例通过"。偏离计划的次数有上限，每一步的过程、结果、截图和偏离都会记录下来。

套件运行器在分派时遵循一条规则：用例有确定性脚本，就优先跑脚本；没有脚本，才交给大模型。**脚本判定为失败时，直接采信结果，不再回落给大模型重试**，因为大模型会"想办法"走通，反而掩盖了真正的回归。

两种模式产出同一格式的结果文件和报告，报告里每一步都附有截图。登录用例和切换语言用例目前都已经稳定回放通过。

## 五、失败了怎么办：先分类，再处置

无人值守的回放，最怕的是半夜跑挂了，第二天面对一堆红色不知道从何查起，更怕的是自动修复把真正的 Bug"修"没了。所以一次失败必须先分类，再决定怎么处理：

| 失败类型 | 表象 | 处置 |
|----------|------|------|
| **真回归**（App 真坏了） | 元素都在，但结果和预期对不上 | 判 FAIL 并告警，**绝不自愈** |
| **定位漂移**（界面改版） | 找不到元素，页面结构变了 | 交给自愈，生成修复建议等人审核 |
| **数据或环境不满足** | 接口报错、数据为空、前置条件不成立 | 判 BLOCKED，不算 FAIL |
| **偶发抖动** | 网络或时序问题，重试即过 | 回放内的等待和重试兜住，不升级 |

这里引入了一个独立于 PASS、FAIL、WARN 之外的第四种结果：**BLOCKED**。它专门用来区分"测试没能成立"和"测试发现了 Bug"。比如登录用例失败了，依赖登录的后续用例都会被标为 BLOCKED，而不是一串 FAIL，这样一眼就能看出真正的问题出在哪一步。用例之间的依赖关系写在用例文件头里，运行器会自动排出执行顺序，依赖失败时 BLOCKED 会沿着依赖链传播。

自愈有一条红线：**它只处理"找不到元素"这类结构漂移，任何改动都以待审核的修改建议落地，由人合并，绝不在半夜自动改测试。** 目前自愈环节还停留在骨架阶段，是下一步的重点。

## 六、几个值得一提的工程细节

**凭据不进对话记录。** 登录需要账号密码，但这些不能出现在大模型的对话里。用例里用占位符代替真实的账号密码，执行到输入那一步时，由一个辅助脚本自己从本地配置文件读取，再直接通过 Appium 填进输入框，真实的值既不经过大模型，也不回显。

**每一步都截图。** 不只在失败时截，而是每一步执行后都截图落盘。失败时可以从报告里逐帧回看，到底是从哪一步开始不对的。

**断言用页面特征，不用具体文案。** 比如判断"登录成功"，看的是底部 Tab 栏是否出现，而不是某个 Tab 叫什么名字。Tab 的名字是后台可配置的，用户数据也会变，绑定具体文案的断言很容易误报。

**首次启动的弹窗。** 每次重新安装 App 后，都会有一串系统权限弹窗和 App 自己的引导弹窗。回放开始前会先做一轮"沉降"，把这些弹窗清理掉；回放过程中，后台还会持续守护，及时处理突然冒出的系统弹窗。

**模型的选择会影响结果。** 我们曾用较小的模型跑登录用例，它在输入凭据那一步，跑去检查系统环境变量，没找到就判定"凭据缺失"直接退出了；换成更强的模型后，它能正确地调用辅助脚本完成输入。大模型主导回放默认使用能力最强的模型，确定性回放则完全不受模型影响，这也是我们尽量把用例固化成脚本的原因之一。

**接入管理后台调度。** E2E 的全量回放已经接入管理后台：QA 可以选择测试包、测试账号和设备，发起单次运行、定时运行或每天重复运行。设备的占用在稳定性测试和 E2E 之间互斥，避免两个任务抢同一台手机。

## 七、另一条路：stub 直驱

### 动机：Appium 的单步成本

对 E2E 回放来说，Appium 一步半秒可以接受。但在探索性任务里就不行了：让大模型自己摸索"进课程详情页把它收藏"，十几步起步，每一步还要叠加一轮大模型推理。

| 操作 | Appium | stub |
|---|---|---|
| 取页面结构 | 1-3 秒 | 约 20ms |
| 点击 | 约 500ms | 约 3ms |
| 截图 | 约 800ms | 约 130ms |

这里的 stub，就是稳定性测试里注入到 App 中、用来给 Fastbot 描述界面的那个组件。既然它已经在 App 进程里，能直接读视图树，为什么不让它也能直接"动手"？我们在它原本只读的基础上，补齐了点击、滚动、返回、长按、输入和截图。速度差距是 50 到 150 倍。

### 能力：在 App 进程里直接"动手"

点击是三级策略，依次尝试：是系统控件（UIControl），就直接触发它的响应事件；挂了点击手势，就直接调用手势的处理方法；是列表的一行，就调用列表的选中回调。返回补上了 iOS 最大的平台差异——它没有系统返回键，stub 通过导航栈的弹出或页面关闭来模拟。滚动则是沿着视图层级向上找到能滚动的容器，直接修改滚动位置，并通知业务侧，分页加载照常触发。

取文本也做了增强。很多第三方的富文本控件不是系统 Label 的子类，按类型判断一律取不到文字，实测课程列表 179 个条目全部没有名字。改为运行时探测控件是否有文本属性之后，所有自定义文本控件都能读出内容了。

### 关键原则：坐标不能交给模型算

这条思路沿用了开源项目 AppAgent：**不让模型输出坐标。** 代码从视图树里筛出可交互的元素，编号后交给模型，模型只回答"点第几个"或"点写着什么的那个"，坐标由代码计算。

从树到"可点元素列表"这一步踩了不少坑，最危险的一个是"静默点错"：一个列表项的中心点恰好落在底部 Tab 栏下面，点击报告成功，页面也确实跳转了，只是跳到了另一个 Tab。工具和模型都不知道自己点错了。修法是计算点击位置时主动避开悬浮遮挡的区域。

另一个反复出现的坑是**序号漂移**：列表多出一项，后面的序号就整体错位，按上一步的序号去点必然点错。所以工具优先按文案定位，序号只留给没有文案的图标按钮，并且每次操作后都要重新获取界面。

### 视觉：不在主循环，而在旁路

纯图标按钮在视图树里没有任何文字。课程详情页导航栏的三个小按钮，类型、尺寸、各项属性完全一致，只有横坐标不同，文本方案理论上无法区分。所以视觉是必需的，关键是让它足够便宜：

| | 整屏截图 | 只裁那一条图标带 |
|---|---|---|
| 体积 | 248 KB | 4.9 KB |
| 编码 token | 3506 | 79 |
| 本地视觉模型耗时 | 45 秒 | 4-9 秒 |

所以截图接口支持裁剪，只在遇到无名图标时调用视觉模型，结果按元素和位置缓存，同一个图标只问一次。

### 边界：stub 做不到的事

stub 的点击直接调用控件的响应方法，不经过系统的事件分发，这决定了它有三个边界。一是**Flutter 和 WebView 内部点不了**：它们没有原生子控件可调，stub 会明确返回"自绘容器"，不会静默失灵。二是**自己重写了触摸处理的控件不响应**，失败时会返回原因，调用方可以降级。三是**输入框只能填、不能提交**：很多 App 的提交按钮在系统键盘上，stub 点不到，所以搜索流程经常走不通，找列表项应该优先滚动查找。

### 自己写循环，还是直接交给 agent

探索的前半程，我们写了一套完整的驱动循环，搭配本地部署的开源模型。结论是：**本地模型的能力不够，循环写得再周到也兜不住。** 它会把多个参数塌缩成一个字符串、看到收藏按钮就报告完成而实际没点、在同一个 Tab 上反复点击。

同样的任务交给 Claude 直接驱动，5 步完成，还会主动截图确认收藏星标变成了实心。差距不只是"模型更聪明"，有些手段是结构性的：按文案而不是序号定位、在代码里循环滚动查找而不是每滚一次问一轮、主动截图自我验证。前两条后来固化成了工具能力，即使换回较弱的模型也能受益。

所以最终形态是一个 MCP 服务加一份使用说明（skill）：不再自己写循环，agent 本身就是循环。

## 八、两条通道怎么选

| | Appium | stub 直驱 |
|---|---|---|
| 速度 | 秒级 | 毫秒级 |
| 保真回放 | 走系统事件分发，保真 | 直接调用响应方法，事件链不完整 |
| Flutter / WebView | 能操作 | 能看见，点不进去 |
| 前提 | Appium 加 WebDriverAgent | 注入了 stub 的测试包 |
| 适合 | E2E 用例的录制、回放、自愈 | 探索性任务、快速试探界面路径 |

两条通道在插件里并存。固定用例的录制和回放走 Appium，保证结果可信；需要 AI 快速摸索的场景走 stub，保证速度。stub 直驱的设计取舍和后来的进展，在下一篇单独展开。

## 九、现状与下一步

目前已经完成的部分：工具选型和最小验证；录制、生成、回放的完整链路；确定性回放引擎和大模型主导回放的双模分派；带每步截图的报告；用例依赖排序和 BLOCKED 传播；管理后台的调度；以及 stub 直驱通道。

接下来的重点有四件：把自愈环节从骨架做成可用的工具；和产品、QA 一起梳理 UMU 的 P0 用例清单；产出一份给开发同学的控件标识埋点约定，按 P0 流程逐步铺开；以及把冒烟用例接入代码合并流程。

Android 侧，团队已有官方的 journey 测试方案，本系列的 E2E 方案目前只覆盖 iOS。

本白皮书是一份技术指南，完整覆盖 AI 智能体的运维生命周期，重点讲部署、扩缩容和生产化。第 4 天讲了评估与可观测性，本篇在此基础上，讨论如何借助稳健的 CI/CD 流水线和可扩展的基础设施建立足够的信任，把智能体推向生产。文中会分析基于智能体的系统从原型走向企业级方案时遇到的挑战，并特别关注 Agent2Agent（A2A）互操作性。本指南面向 AI/ML 工程师、DevOps 从业者和系统架构师，提供可落地的实践经验。

## 简介：从原型到生产

做一个 AI 智能体原型，几分钟甚至几秒钟就够了。但要把这个巧妙的演示变成业务可以依赖、值得信任的生产级系统呢？真正的工作这才开始。欢迎来到**生产落地的“最后一公里”**。我们在服务客户的实践中反复看到：大约 80% 的工作量并不花在智能体的核心智能上，而是花在让它可靠、安全运行所需的基础设施、安全和验证上。

跳过这最后几步，可能会引发不少问题。比如：

**• 客服智能体被人骗着免费送出商品**，只因为你忘了设置合适的护栏。

**• 用户发现能通过你的智能体访问内部机密数据库**，原因是身份验证配置不当。

**• 智能体一个周末就跑出一大笔费用账单**，可谁也说不清原因，因为你根本没设监控。

**• 昨天还运行得好好的关键智能体，今天突然罢工**，团队手忙脚乱，因为根本没有持续评估。

这些不只是技术问题，而是重大的业务事故。DevOps 和 MLOps 的原则固然是重要基础，但单靠它们还不够。部署智能体系统会带来一类新挑战，要求**运维方法本身随之演进**。与传统 ML 模型不同，智能体能自主交互、带有状态，执行路径也是动态的。

由此带来一些独特的运维难题，需要专门的应对策略：

**• 动态工具编排：** 智能体边执行边挑选工具，它的“轨迹”是临时拼出来的。系统每次的行为都不一样，因此需要稳健的版本管理、访问控制和可观测性。

**• 可扩展的状态管理：** 智能体能在多次交互之间记住信息。要在大规模下安全、一致地管理会话和记忆，是一个复杂的系统设计问题。

**• 难以预测的成本与延迟：** 智能体找答案的路径可能千差万别。没有精细的预算控制和缓存，它的成本和响应时间极难预测，也极难控制。

要顺利应对这些挑战，你需要一个由三大支柱撑起的基础：**自动化评估**、**自动化部署（CI/CD）**和**全面的可观测性**。

本白皮书就是一份分步指南，带你打好这个基础，一路走到生产！我们先从上线前的必备工作讲起：如何搭建自动化 CI/CD 流水线，如何把严格的评估作为关键的质量检查。接着深入讨论智能体在真实环境中运行时的挑战，涵盖扩缩容、性能调优和实时监控的策略。最后，我们会展望令人期待的多智能体系统，介绍 Agent-to-Agent 协议，并探讨怎样让多个智能体安全、高效地通信。

## 人员与流程

聊了这么多 CI/CD、可观测性和动态流水线，为什么还要专门讲人员和流程？因为再好的技术，没有合适的团队去构建、管理和治理，也发挥不了作用。

客服智能体不会凭空就懂得不送免费商品，是 AI 工程师和提示工程师设计并实现了护栏。机密数据库也不是靠某个抽象概念保住的，是云平台团队配好了身份验证。每个成功的生产级智能体背后，都有一支配合默契的专家团队。本节就来介绍其中的关键角色。

![][image2]

图 1：“Ops”位于人员、流程与技术三者的交汇处

在传统的 MLOps 体系中，主要涉及以下几个团队：

**• 云平台团队：** 由云架构师、管理员和安全专家组成，负责管理底层云基础设施、安全和访问控制。团队按最小权限原则给工程师和服务账号分配角色，确保他们只能访问必要的资源。

**• 数据工程团队：** 由数据工程师和数据所有者组成，负责构建和维护数据流水线，处理数据接入、准备和质量标准。

**• 数据科学与 MLOps 团队：** 包括做实验、训练模型的数据科学家，以及用 CI/CD 大规模自动化端到端 ML 流水线（如预处理、训练、后处理）的 ML 工程师。MLOps 工程师则负责构建和维护标准化的流水线基础设施，为他们提供支撑。

**• 机器学习治理：** 这是一个集中化的职能，成员包括产品负责人和审计人员。他们监督 ML 生命周期，统一存放制品和指标，以保证合规、透明和可问责。

生成式 AI 又给这个体系增加了一层复杂度，也带来了新的专业角色：

**• 提示工程师：** 这个职位名称在业内仍在演变。这类人员既懂编写提示词的技术，又有深厚的领域知识。他们负责定义该向模型提出什么问题、期望得到什么答案。实际工作中，这件事也可能由 AI 工程师、领域专家或专职人员来做，取决于组织的成熟度。

**• AI 工程师：** 负责把 GenAI 方案推向生产，构建稳健的后端系统，其中包括大规模评估、护栏以及 RAG/工具集成。

**• DevOps/应用开发者：** 负责构建前端组件和易用的界面，并与 GenAI 后端对接。

组织的规模和结构会影响这些角色的划分：小公司里一个人可能身兼数职，成熟的组织则会有分工更细的团队。无论哪种情况，有效协调这些不同角色，都是打牢运维基础、让传统 ML 和生成式 AI 项目顺利投产的关键。

## 通往生产之路

团队有了，接下来看流程。怎样把这些专家的工作整合成一个可信、可靠、能交付给用户的系统？

答案是一套严谨的上线前流程，它建立在一条核心原则之上：**评估门控部署（Evaluation-Gated Deployment）**。思路简单却有力：任何智能体版本在到达用户之前，都必须先通过全面评估，证明自身的质量和安全性。在上线前阶段，我们用自动化带来的确定性取代人工带来的不确定性。这个阶段由三大支柱组成：充当质量门禁的严格评估流程、负责执行门禁的自动化 CI/CD 流水线，以及为上线最后一步降低风险的安全发布策略。

## 把评估当作质量门禁

为什么智能体需要专门的质量门禁？因为会推理、会自适应的系统，靠传统软件测试是测不全的。而且评估智能体和评估 LLM 不是一回事：不仅要看最终答案，还要看它完成任务时整条推理和行动的轨迹。一个智能体的工具可能 100 个单元测试全部通过，却仍会因为选错工具或答案出现幻觉而彻底失败。我们要评估的是它的*行为质量*，而不只是功能是否正确。这道门禁主要有两种实现方式：

**1. 人工“PR 前”评估：** 适合追求灵活性、或刚开始做评估的团队，质量门禁靠团队流程来保证。提交拉取请求（PR）之前，**AI 工程师**或**提示工程师**（或组织里任何负责智能体行为的人）先在本地跑一遍评估套件，然后把生成的性能报告（新智能体与生产基线的对比）链接到 PR 描述里。这样一来，评估结果就成了人工评审时必须提供的制品。评审者通常是另一位 **AI 工程师**或**机器学习治理人员**，他们不仅要审代码，还要审查智能体行为的变化，看是否违反护栏、是否存在提示注入漏洞。

**2. 自动化的流水线内门禁：** 对于成熟团队，评估框架由**数据科学与 MLOps 团队**构建和维护，直接集成进 CI/CD 流水线。评估一旦失败，部署会被自动拦截，以程序化的方式严格执行**机器学习治理**团队定下的质量标准。这种做法牺牲了人工评审的灵活性，换来了自动化的一致性。CI/CD 流水线可以配置成自动触发评估任务，把新智能体的回答与黄金数据集进行比对。如果“工具调用成功率”或“有用性”等关键指标低于预设阈值，部署就会被程序自动拦截。

不管用哪种方式，原则都一样：没有经过质量检查，任何智能体都不能进入生产。至于具体衡量什么、如何搭建评估框架，我们已在**第 4 天：智能体质量：可观测性、日志、追踪、评估、指标**中详细讨论过。那一篇从构建“黄金数据集”（一组精心挑选、有代表性的测试用例，用来评估智能体的预期行为和护栏合规情况），讲到实现 LLM-as-a-judge（以 LLM 为评审）技术，最后讲到借助 Vertex AI Evaluation 这类服务来支撑评估。

## 自动化 CI/CD 流水线

AI 智能体是一个复合系统，除了源代码，还包括提示词、工具定义和配置文件。这种复杂性带来了不小的挑战：怎样保证改了提示词不会拖累某个工具的表现？怎样在这些制品交到用户手上之前，测试它们之间的相互影响？

解决办法是 CI/CD（持续集成/持续部署）流水线。它不只是一段自动化脚本，更是一套结构化流程，帮助团队里不同角色协同应对复杂性、保证质量。它的做法是分阶段测试变更，在智能体发布给用户之前一步步积累信心。

稳健的流水线像一个漏斗，尽可能早、尽可能低成本地发现错误，这种做法常被称为“左移”。它把快速的合并前检查，与更全面、更耗资源的合并后部署区分开。这种渐进式流程通常分为三个阶段：

**1. 阶段 1：合并前集成（CI）**。流水线的首要任务，是给发起拉取请求的 **AI 工程师**或**提示工程师**快速反馈。这个 CI 阶段自动触发，是主分支的守门人，负责运行单元测试、代码 lint 和依赖扫描等快速检查。关键在于，这里也是

运行提示工程师设计的**智能体质量评估套件**的最佳阶段。这样在变更合并之前，就能立即知道它在关键场景下让智能体变好还是变差。在这里拦住问题，就不会污染主分支。用 Agent Starter Pack（ASP）生成的 PR 检查配置模板，就是用 Cloud Build 实现这一阶段的实际例子。

**2. 阶段 2：合并后的预发环境验证（CD）**。变更通过全部 CI 检查（包括性能评估）并合并后，关注点就从代码和性能是否正确，转向整个集成系统是否具备运维就绪度。持续部署（CD）流程通常由 **MLOps 团队**负责，它把智能体打包，部署到预发（staging）环境，也就是对生产环境的高保真复刻。这里会运行更全面、更耗资源的测试，比如**负载测试**和对接远程服务的**集成测试**。这也是内部用户测试（常称“dogfooding”）的关键阶段：公司内部人员可以先和智能体交互，在它到达最终用户之前给出定性反馈。这样就能确保智能体作为一个*集成系统*，在进入发布评估之前，已在接近生产的条件下运行得可靠、高效。ASP 的预发部署模板展示了这类部署的示例。

**3. 阶段 3：带门禁的生产部署**。智能体在预发环境中经过充分验证后，最后一步就是部署到生产。这一步几乎从不完全自动化，通常需要**产品负责人**最终签字，确保有人参与把关（human-in-the-loop）。审批通过后，在预发环境中测试验证过的那个部署制品，会被原样提升到生产环境。用 ASP 生成的生产部署模板展示了这一阶段的做法：取出已验证的制品，在适当的保护措施下部署到生产。

![][image4]

图 3：CI/CD 流程的各个阶段

要让这三阶段 CI/CD 流程跑起来，需要稳健的自动化基础设施和妥善的密钥管理。这套自动化主要依靠两项关键技术：

**• 基础设施即代码（IaC）：** Terraform 等工具以编程方式定义环境，确保环境一致、可复现，并纳入版本控制。比如，用 Agent Starter Pack 生成的这个模板，提供了完整智能体基础设施的 Terraform 配置，涵盖 Vertex AI、Cloud Run 和 BigQuery 资源。

**• 自动化测试框架：** Pytest 等框架在每个阶段执行测试和评估，处理智能体特有的制品，比如对话历史、工具调用日志和动态推理轨迹。

此外，工具的 API 密钥这类敏感信息，不应硬编码在代码仓库里，而应交给 Secret Manager 这类服务安全管理，在运行时注入智能体的环境。

## 安全发布策略

上线前的全面检查必不可少，但到了真实环境，总会冒出意料之外的问题。与其一次把 100% 的用户切过去，不如通过渐进式发布并密切监控来降低风险。

下面四种经过验证的模式，能帮助团队对部署更有把握：

**• 金丝雀发布（Canary）：** 先放给 1% 的用户，重点监控提示注入和异常的工具调用。之后逐步扩大，或随时立即回滚。

**• 蓝绿部署（Blue-Green）：** 同时运行两套完全相同的生产环境。流量走“蓝”环境，新版本部署到“绿”环境，然后瞬间切换。一旦出问题就切回去，零停机，秒级恢复。

**• A/B 测试：** 用真实业务指标对比不同版本的智能体，用数据来做决策。测试对象可以是内部用户，也可以是外部用户。

**• 功能开关（Feature Flags）：** 代码先部署上去，但发布节奏动态控制，新能力先给选定的用户试用。

这些策略都有一个共同基础：**严格的版本管理**。每个组件都必须有版本，包括代码、提示词、模型端点、工具 schema、记忆结构，甚至评估数据集。这样即使有了各种防护仍然出了问题，也能立刻回滚到已知的良好状态。把它当作生产环境的“撤销”按钮吧！

你可以用 Agent Engine 或 Cloud Run 部署智能体，再借助 Cloud Load Balancing 在多个版本之间分配流量，或对接其他微服务。Agent Starter Pack 提供了开箱即用的 GitOps 工作流模板：每次部署就是一次 git commit，每次回滚就是一次 git revert，代码仓库成为当前状态和完整部署历史的唯一事实来源。

## 从一开始就把安全做进去

安全的部署策略能防住 bug 和故障，但智能体还有一个独特的挑战：它能自主推理和行动。即使部署得再完美，如果构建时没有做好安全和责任方面的措施，它照样可能造成危害。因此，全面的治理策略必须从第一天就融入进来，而不是事后再补。

传统软件按预定路径运行，智能体则会自己做决策。它要理解含糊的请求，调用多个工具，还要在多个会话之间保持记忆。这种自主性带来了一些特有的风险：

**• 提示注入与越权行为：** 恶意用户可能诱导智能体执行非预期操作，或绕过限制。

**• 数据泄露：** 智能体可能在回复或调用工具时，无意中泄露敏感信息。

**• 记忆投毒：** 一旦智能体的记忆里存入了虚假信息，之后的所有交互都可能被污染。

好在已有一些框架应对这些挑战，比如 Google 的 Secure AI Agents 方法和 Google 安全 AI 框架（SAIF），它们通过三层防御来解决问题：

**1. 策略定义与系统指令（智能体的“宪法”）：** 第一步是定义策略，明确哪些行为是期望的、哪些是不允许的。这些策略会被写进**系统指令（System Instructions，SI）**，作为智能体的核心“宪法”。

**2. 护栏、防护措施与过滤（执行层）：** 这一层是强制拦截机制。

**• 输入过滤：** 使用分类器和 Perspective API 这类服务分析提示词，在恶意输入到达智能体之前就拦下来。

**• 输出过滤：** 智能体生成回复后，由 **Vertex AI 内置的安全过滤器**做最后一道检查，排查有害内容、PII 或违反政策的内容。例如，回复发给用户之前，会先经过 Vertex AI 内置的安全过滤器。过滤器可以配置为拦截包含特定 PII、恶毒言论或其他有害内容的输出。

**• 人工介入（HITL）升级：** 遇到高风险或含义不明的操作，系统必须暂停，并升级给人工审核和批准。

**3. 持续保障与测试：** 安全不是一次配置就完事，需要持续评估、不断调整。

**• 严格评估：** 模型或其安全系统的任何改动，都必须触发一次完整的综合评估流水线（基于 **Vertex AI Evaluation**）。

**• 专项 RAI 测试：** 通过构建专用数据集或使用模拟智能体，严格测试特定风险，包括**中立观点（NPOV）评估**和**公平性（Parity）评估**。

**• 主动红队测试：** 通过有创意的人工测试和 AI 驱动的**基于人设的模拟**，主动尝试攻破安全系统。

## 生产环境中的运维

智能体上线了。接下来，重心从开发转向一个性质完全不同的挑战：在与成千上万用户交互的同时，**保持系统可靠**、**控制成本**，**并确保安全**。传统服务按可预测的逻辑运行，智能体却是一个自主的行动者。它可能走出意想不到的推理路径，这意味着它可能在无人直接监督的情况下出现涌现行为，并不断累积成本。

管理这种自主性，需要一种不同的运维模式。高效的团队不做静态监控，而是采用一个持续循环：实时观察（Observe）系统行为，采取行动（Act）维持性能和安全，再根据生产中的经验演进（Evolve）智能体。这个闭环，正是在生产中成功运营智能体的核心方法。

## 观察：智能体的感官系统

要信任并管好一个自主智能体，首先得了解它的运行过程。可观测性提供的正是这种关键洞察，它是后续“行动”和“演进”阶段的感官系统。扎实的可观测性实践建立在三大支柱上，三者配合，才能完整呈现智能体的行为：

**• 日志（Logs）：** 细粒度、如实记录发生了什么的“日记”，每次工具调用、每个错误和决策都记在里面。

**• 追踪（Traces）：** 把一条条日志串起来的“叙事线”，揭示智能体为什么采取某个行动的因果路径。

**• 指标（Metrics）：** 汇总后的“成绩单”，在规模层面概括性能、成本和运维健康度，反映系统整体表现如何。

以 Google Cloud 为例，这些能力由运维套件提供：用户的每个请求会在 Cloud Trace 中生成唯一 ID，把 Vertex AI Agent Engine 调用、模型调用和工具执行串联起来，并显示各自耗时。详细日志写入 Cloud Logging，Cloud Monitoring 仪表盘则在延迟超过阈值时告警。Agent Development Kit（ADK）内置 Cloud Trace 集成，可自动为智能体的各项操作埋点。

落实这三大支柱后，我们就不再摸黑运维，而是能清晰地、用数据看清智能体的行为，为在生产中有效管理它打下基础。（这些概念的完整讨论，请参阅**智能体质量：可观测性、日志、追踪、评估、指标**。）

## 行动：运维控制的抓手

只观察不行动，仪表盘再贵也只是摆设。“行动”阶段讲的是实时干预，也就是根据观察结果，动用各种抓手来管理智能体的性能、成本和安全。

可以把“行动”理解为系统的自动化反射，目的是实时维持稳定。而后面要讲的“演进”，则是从行为中学习、从根本上把系统做得更好的战略过程。

智能体是自主的，你不可能预先为每种结果写好程序。你需要做的，是构建稳健的机制，在生产中影响它的行为。这些运维抓手主要分两类：管理系统健康，以及管理风险。

## 管理系统健康：性能、成本与规模

与传统微服务不同，智能体的工作负载是动态的、有状态的。要管好它的健康状况，就需要一套应对这种不确定性的策略。

**• 面向规模设计：** 基础是把智能体的逻辑和状态解耦。

**• 水平扩展：** 把智能体设计成无状态的容器化服务。状态放在外部，任何实例都能处理任何请求，Cloud Run 或托管的 Vertex AI Agent Engine Runtime 这类无服务器平台就能自动扩缩容。

**• 异步处理：** 对于耗时较长的任务，用事件驱动模式把工作卸载出去。这样复杂任务在后台处理，智能体依然能及时响应。比如在 Google Cloud 上，服务可以把任务发布到 Pub/Sub，再由它触发 Cloud Run 服务做异步处理。

**• 外置状态管理：** LLM 本身是无状态的，所以记忆必须持久化到外部，这一点没有商量余地。这也引出一个关键的架构选择：**Vertex AI Agent Engine** 内置了持久化的会话和记忆服务；**Cloud Run** 则更灵活，可以直接对接 AlloyDB 或 Cloud SQL 等数据库。

**• 平衡相互冲突的目标：** 扩容总要在三个相互冲突的目标之间取舍：速度、可靠性和成本。

**• 速度（延迟）：** 让智能体并行工作、积极缓存结果，并用更小、更高效的模型处理常规任务，以保持响应速度。

**• 可靠性（应对故障）：** 智能体必须能应对临时故障。调用失败时自动重试，最好采用*指数退避*，给服务留出恢复时间。这要求工具设计成“可安全重试”的（*幂等*），以免出现重复扣款之类的 bug。

**• 成本：** 缩短提示词、简单任务换用更便宜的模型、把请求合并发送（批处理），让智能体的成本保持在可承受范围内。

## 管理风险：安全响应预案

智能体能自主行动，所以你需要一套能快速止损的预案。一旦发现威胁，响应应遵循清晰的顺序：**遏制、研判、解决**。

第一步是**立即遏制**。首要任务是止损，通常靠“熔断器”，也就是用一个功能开关立刻禁用出问题的工具。

第二步是**研判**。威胁得到遏制后，把可疑请求转入人工介入（HITL）审核队列，调查这次攻击的范围和影响。

最后，重心转向**彻底解决**。团队开发补丁，比如更新输入过滤器或系统提示词，然后通过自动化 CI/CD 流水线部署，确保修复经过充分测试，再彻底堵住漏洞。

## 演进：从生产中学习

“行动”阶段提供的是系统即时的、战术层面的反射，“演进”阶段则着眼于长期的、战略层面的改进。它从可观测性数据中积累的模式和趋势入手，追问一个关键问题：“怎样从根源上修复，让这个问题再也不出现？”

到了这一步，你不再被动应对生产事故，而是主动让智能体变得更聪明、更高效、更安全。你要把“观察”阶段得到的原始数据，转化为智能体在架构、逻辑和行为上的长期改进。

## 演进的引擎：自动化的上线通道

来自生产的洞察，只有能迅速落地才有价值。就算你发现 30% 的用户在某项任务上失败，如果团队要花六个月才能上线修复，这个发现也毫无用处。

这时，你在上线前阶段（第 3 节）搭建的**自动化 CI/CD 流水线**，就成了运维闭环中最关键的一环。它是驱动快速演进的引擎。有了快速、可靠的上线通道，从观察到改进的闭环就能以小时或天计，而不是以周或月计。

当你发现可以改进的地方时，无论是优化提示词、增加新工具，还是更新安全护栏，流程都应该是：

**1. 提交变更：** 把拟定的改进提交到纳入版本控制的代码仓库。

**2. 触发自动化：** 这次提交会自动触发 CI/CD 流水线。

**3. 严格验证：** 流水线基于更新后的数据集，跑完整套单元测试、安全扫描和智能体质量评估套件。

**4. 安全部署：** 验证通过后，按安全发布策略把变更部署到生产。

这套自动化流程，让演进从缓慢、高风险的手工项目，变成快速、可重复、由数据驱动的过程。

## 演进流程：从洞察到上线改进

**1. 分析生产数据：** 从生产日志中找出用户行为、任务成功率和安全事件的趋势。

**2. 更新评估数据集：** 把生产中的失败案例变成明天的测试用例，扩充你的黄金数据集。

**3. 改进并部署：** 提交改进，触发自动化流水线，无论是优化提示词、增加工具，还是更新护栏。

由此形成良性循环：用户每交互一次，智能体就进步一点。

![][image5] **An Evolve Loop in Action**

**演进循环实例**

某零售智能体的日志显示（**观察**），15% 的用户在询问“相似商品”时会收到报错。产品团队随即建了一张高优先级工单（**行动**）。**演进**阶段开始：团队根据生产日志，为评估数据集新增一条会失败的测试用例。一位 **AI 工程师**优化了智能体的提示词，并新增了一个更稳健的相似度搜索工具。变更提交后，通过了 CI/CD 流水线中已更新的评估套件，再以金丝雀方式安全发布。不到 48 小时，用户的问题就解决了。

## 安全也要演进：生产反馈闭环

基础的安全与责任框架虽然在上线前阶段（第 3.4 节）就已建立，但这项工作永远没有真正的终点。安全不是一张静态的检查清单，而是一个动态、持续调整的过程。生产环境才是终极试验场，在那里收集到的洞察，是加固智能体、抵御真实威胁的关键。

这时，**观察** → **行动** → **演进**的循环对安全至关重要。这个过程是演进流程的直接延伸：

**1. 观察：** 监控和日志系统发现了一个新的威胁向量。它可能是一种能绕过现有过滤器的新型提示注入手法，也可能是一次导致轻微数据泄露的意外交互。

**2. 行动：** 安全应急团队立即遏制威胁（见第 4.2 节）。

**3. 演进：** 这是保持长期韧性的关键一步。安全方面的洞察会反馈到开发生命周期中：

**• 更新评估数据集：** 把这种新的提示注入攻击作为固定测试用例，加入评估套件。

**• 完善护栏：** 由**提示工程师**或 **AI 工程师**改进智能体的系统提示词、输入过滤器或工具使用策略，堵住新的攻击向量。

**• 自动化部署：** 工程师提交变更，触发完整的 CI/CD 流水线。更新后的智能体经过扩充后评估集的严格验证，再部署到生产，漏洞随之封堵。

这形成了一个强有力的反馈闭环：每一次生产事故都让智能体更强、更有韧性，你的安全姿态也从被动防守转向持续、主动的改进。

想进一步了解负责任的 AI（Responsible AI）以及如何保护 AI 智能体系统，请参阅白皮书《Google's Approach for Secure AI Agents》和《Google 安全 AI 框架（SAIF）》。

## 超越单个智能体的运维

你已经掌握了在生产中运营单个智能体的方法，也能快速交付。但当组织里的专用智能体增加到几十个，而且由不同团队用不同框架构建时，新问题就来了：这些智能体之间无法协作。下一节将探讨标准化协议如何把这些孤立的智能体连成一个可互操作的生态，借助智能体协作释放成倍的价值。

## A2A：复用与标准化

你已经在组织里构建了几十个专用智能体：客服团队有自己的支持智能体，分析团队做了预测系统，风控团队搭了欺诈检测。但问题在于，这些智能体彼此无法对话，原因可能是它们基于不同的框架、属于不同的项目，甚至部署在完全不同的云上。

这种隔绝造成了巨大的浪费。每个团队都在重复造同样的能力，关键洞察被锁在各自的孤岛里。你需要的是互操作性：任何智能体都能调用任何其他智能体的能力，不管是谁构建的、用的什么框架。

要解决这个问题，需要一套有章法的标准化方案，它建立在两个各有侧重、又相互补充的协议之上。**模型上下文协议（Model Context Protocol，MCP）**我们已在**智能体工具与基于 MCP 的互操作性**中详细介绍过，它为工具集成提供了通用标准，但不足以支撑智能体之间复杂、有状态的协作。**Agent2Agent（A2A）**协议正是为解决这个问题而设计的，目前由 Linux 基金会管理。

两者的区别非常关键。如果你只需要一个简单的无状态函数，比如获取天气数据或查询数据库，那么一个支持 MCP 的工具就够了。但如果你要委派一个复杂目标，比如“分析上季度的客户流失，并给出三条干预策略”，你需要的就是一个能通过 A2A 自主推理、规划和行动的智能伙伴。简单说，MCP 让你说“做这件具体的事”，A2A 让你说“达成这个复杂目标”。

## A2A 协议：从概念到落地

A2A 协议的目标是打破组织孤岛，让智能体之间无缝协作。设想一个场景：欺诈检测智能体发现了可疑活动，为了掌握完整背景，它需要另一个交易分析智能体的数据。没有 A2A，就得靠人工分析师手动打通，可能耗时数小时；有了 A2A，智能体之间自动协作，几分钟就能解决问题。

协作的第一步，是找到合适的智能体来委派任务。这要靠智能体卡片（Agent Card）。它是一份标准化的 JSON 描述，相当于每个智能体的名片，说明这个智能体能做什么、有哪些安全要求和技能，以及如何访问它（url）。这样，生态中的任何智能体都能动态发现其他智能体。下面是一个 Agent Card 示例：

```json
{
  "name": "check_prime_agent",
  "version": "1.0.0",
  "description": "An agent specialized in checking whether numbers are prime",
  "capabilities": {},
  "securitySchemes": {
    "agent_oauth_2_0": {
      "type": "oauth2"
    }
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "prime_checking",
      "name": "Prime Number Checking",
      "description": "Check if numbers are prime using efficient algorithms",
      "tags": ["mathematical", "computation", "prime"]
    }
  ],
  "url": "http://localhost:8001/a2a/check_prime_agent"
}
```

智能体对外开放后，其他任何智能体都能通过引用它的 AgentCard 来调用它。比如，客服智能体现在可以直接查询远程的商品目录智能体，而无需了解其内部实现。

```python
# Example using ADK: Consuming a remote agent via A2A
# 使用 ADK 的示例：通过 A2A 消费远程智能体

from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

prime_agent = RemoteA2aAgent(
    name="prime_agent",
    description="Agent that handles checking if numbers are prime.",
    agent_card="http://localhost:8001/a2a/check_prime_agent/.well-known/agent-card.json"
)
```

代码片段 3：用 ADK 的 RemoteA2aAgent 类连接并调用远程智能体

这让强大的层级化组合成为可能。根智能体可以同时编排一个处理简单任务的本地子智能体，和一个通过 A2A 接入的远程专用智能体，从而组成能力更强的系统。

```python
# Example using ADK: Hierarchical agent composition
# 使用 ADK 的示例：层次化智能体组合

# ADK Local sub-agent for dice rolling
# 用于掷骰子的 ADK 本地子智能体
roll_agent = Agent(
    name="roll_agent",
    instruction="You are an expert at rolling dice."
)

# ADK Remote A2A agent for prime checking
# 用于质数检查的 ADK 远程 A2A 智能体
prime_agent = RemoteA2aAgent(
    name="prime_agent",
    agent_card="http://localhost:8001/.well-known/agent-card.json"
)

# ADK Root orchestrator combining both
# 组合两者的 ADK 根编排器
root_agent = Agent(
    name="root_agent",
    instruction="""Delegate rolling dice to roll_agent, prime checking to prime_agent.""",
    sub_agents=[roll_agent, prime_agent]
)
```

不过，要实现这种程度的自主协作，有两项必不可少的技术要求。第一是**分布式追踪**：每个请求都带有唯一的 trace ID，这对跨多个智能体调试、保持完整连贯的审计记录至关重要。第二是稳健的**状态管理**：A2A 交互本质上是有状态的，需要一个完善的持久化层来跟踪进度、保证事务完整性。

**A2A 最适合需要长期服务契约的正式跨团队集成**。对于单个应用内部紧密耦合的任务，**轻量的本地子智能体往往仍是更高效的选择**。随着生态逐渐成熟，新建的智能体应当原生支持这两种协议，确保每个新组件一上线就能被发现、可互操作、可复用，让整个系统的价值不断叠加。

## A2A 与 MCP 如何协同

图 4：A2A 与 MCP 协作一览

A2A 和 MCP 不是互相竞争的标准，而是互补的协议，分别工作在不同的抽象层级。区别在于智能体在和什么打交道。MCP 面向**工具和资源**，也就是输入输出定义明确、结构化的基础能力，比如计算器或数据库 API。A2A 面向其他**智能体**，也就是能推理、规划、使用多种工具、保持状态以达成复杂目标的自主系统。

最强大的智能体系统会在分层架构中同时使用这两种协议。一个应用可能主要用 A2A 编排多个智能体之间的高层协作，而每个智能体内部再用 MCP 与自己的那套工具和资源交互。

打个实际的比方：一家由自主 AI 智能体运营的汽车修理厂。

**1. 用户到智能体（A2A）：** 顾客通过 A2A 与“店长”智能体沟通，描述一个笼统的问题：“我的车有咔嗒咔嗒的异响。”

**2. 智能体到智能体（A2A）：** 店长经过多轮问诊对话，再通过 A2A 把任务委派给专门的“技师”智能体。

**3. 智能体到工具（MCP）：** 技师智能体要执行具体操作了。它通过 MCP 调用各种专用工具：在诊断仪上运行 `scan_vehicle_for_error_codes()`，用 `get_repair_procedure()` 查询维修手册数据库，用 `raise_platform()` 操作举升机。

**4. 智能体到智能体（A2A）：** 诊断完问题后，技师智能体确认需要更换一个零件。它通过 A2A 联系外部的“零件供应商”智能体，询问是否有货并下单。

在这个流程中，A2A 负责顾客、修理厂各智能体和外部供应商之间更高层的、对话式的、面向任务的交互；MCP 则提供标准化的“管线”，让技师智能体能可靠地使用各种结构化的专用工具完成工作。

## 注册表架构：何时建、怎么建

为什么有的组织要建注册表，有的却不需要？答案在于规模和复杂度。只有五十个工具时，手动配置完全够用。可一旦工具多达五千个、分散在不同团队和环境中，你就会遇到工具发现问题，必须用系统化的方案来解决。

**工具注册表（Tool Registry）**借助 MCP 这类协议，把从函数到 API 的所有资产统一编目。你不必让智能体直接面对成千上万个工具，而是为它们整理精选清单。由此形成三种常见模式：

**• 通用型智能体：** 访问完整目录，用速度和准确性换取覆盖面。**• 专家型智能体：** 只用预先定义的子集，换取更好的表现。**• 动态型智能体：** 在运行时查询注册表，适配新工具。

它最大的好处是方便人来查找：开发者可以先搜索已有工具，避免重复造轮子；安全团队可以审计工具的访问权限；产品负责人可以了解自家智能体具备哪些能力。

**智能体注册表（Agent Registry）**把同样的思路用在智能体上，采用 A2A 的 AgentCard 等格式。它帮助团队发现并复用已有的智能体，减少重复劳动，也为智能体之间的自动委派打下基础，不过这仍是一种新兴模式。

注册表带来了发现和治理能力，代价是维护成本。可以先不建，等生态规模大到需要集中管理时再建！

注册表决策框架

**工具注册表：** 当工具发现成为瓶颈，或安全上需要集中审计时再建。

**智能体注册表：** 当多个团队需要在不紧密耦合的前提下发现和复用专用智能体时再建。

## 融会贯通：AgentOps 生命周期

现在可以把这些支柱拼成一套完整、连贯的参考架构了！生命周期从**开发者内循环**开始：在本地快速测试、做原型，打磨智能体的核心逻辑。变更就绪后，进入正式的上线前流程，由自动化评估门禁基于黄金数据集验证其质量和安全性。之后通过安全发布进入生产。在生产中，全面的可观测性采集真实数据，为持续演进的循环提供养料，把每一条洞察都转化为下一次改进。

如果想全面了解如何让 AI 智能体投入运营，包括评估、工具管理、CI/CD 标准化和有效的架构设计，可以观看 Google Cloud 官方 YouTube 频道上的视频 AgentOps: Operationalize AI Agents。

## 结论：用 AgentOps 跨越最后一公里

把 AI 原型变成生产系统，是一场组织层面的转型，需要一种新的运维方法：**AgentOps**。

大多数智能体项目倒在“最后一公里”，原因不在技术，而在于低估了自主系统的运维复杂度。本指南给出了跨越这道鸿沟的路线：首先，以**人员与流程**作为治理基础；其次，用基于评估门控部署的**上线前**策略，把高风险的发布自动化；上线后，借助持续的**观察** → **行动** → **演进**循环，让每次用户交互都可能成为洞察；最后，通过**互操作性**协议把孤立的智能体连成协作的智能生态，让系统规模化。

眼前的收益，比如防住一次安全事件、实现快速回滚，已足以证明这笔投入值得。但真正的价值在于速度。成熟的 AgentOps 实践能让团队在几小时而不是几周内上线改进，让一次性的静态部署变成持续演进的产品。

## 下一步怎么走

**• 如果你刚起步，** 先打好基础：建立第一个评估数据集，搭好 CI/CD 流水线，建立全面的监控。Agent Starter Pack 是很好的起点，几分钟就能创建一个可直接用于生产、已内置这些基础能力的智能体项目。

**• 如果你正在规模化，** 就要把实践再提升一级：把从生产洞察到上线改进的反馈闭环自动化，并统一采用可互操作的协议，构建一个有机的生态，而不只是零散的单点方案。

下一个前沿，不只是把单个智能体做得更好，而是编排能学习、能协作的复杂多智能体系统。AgentOps 这套运维方法，正是实现这一切的基础。

希望这份指南能帮助你构建下一代智能、可靠、值得信赖的 AI。跨越最后一公里，不是项目的最后一步，而是创造价值的第一步！

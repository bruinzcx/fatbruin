## 一、为什么要先看地图？

"测试"这个词太大了。同样一句"我们要加测试"，后端同学指的通常是单元测试，用来覆盖接口逻辑；iOS 开发可能想的是 XCTest，也可能是 UI 自动化；QA 嘴里的"做测试"，可能是手动回归，也可能是写自动化脚本；而老板说"提升质量"，往往是以上全部，再加上线上监控。大家都在说测试，说的却未必是同一件事。

没有一张完整的地图，很容易在某个角落反复投入，却对其他盲区毫无察觉。比如单元测试写得很扎实，却从没在真机上长时间跑过；或者 E2E 脚本覆盖了所有核心流程，却不知道 App 在低端机上一跑就被系统杀掉。

理解 APP 测试，可以从两个维度入手。一个是**测什么**：功能是否正确、运行是否稳定、换设备是否兼容、速度和资源消耗如何、有没有安全漏洞。另一个是**怎么测**：靠人手动还是靠自动化，把 App 当黑盒还是深入代码做白盒，在发版前的线下环境测还是在线上真实用户中观察。下面按"测什么"逐一展开，"怎么测"会穿插在各个部分里。

## 二、维度一：功能正确性测试

这是最基础的一层，回答的是"功能对不对"。按测试的粒度从小到大，可以分成四层，每一层都有它擅长和无能为力的地方。

### 第一层：单元测试（Unit Test）

单元测试针对的是单个函数或类的逻辑，并且把它和外部依赖完全隔离开。比如一个价格格式化函数，可以这样测：

```swift
// 例：测试一个价格格式化函数
func testPriceFormat() {
    XCTAssertEqual(formatPrice(9900), "¥99.00")
    XCTAssertEqual(formatPrice(0), "¥0.00")
    XCTAssertEqual(formatPrice(-100), "¥-1.00")  // 边界 case
}
```

因为不依赖网络、设备和数据库，单元测试跑得极快，几千个用例几秒钟就能跑完，发现的是纯粹的逻辑错误。它的边界也很清楚：模块之间怎么配合、界面渲染是否正确、网络请求是否正常，都不在它的视野里。所以它最适合业务逻辑层，比如 ViewModel、Service 和各种工具函数，而不适合纯 UI 层。常用工具是 iOS 的 XCTest、Android 的 JUnit，以及 Dart 层的 Flutter Test。

### 第二层：集成测试（Integration Test）

单元测试证明了每个零件单独是好的，但零件拼在一起未必严丝合缝。集成测试要验证的，就是模块之间的接口是否对齐：

```
单元测试中：
  UserService 测过了 ✓
  NetworkClient 测过了 ✓

集成测试验证：
  UserService 调用 NetworkClient，
  拿到真实响应后，数据解析和状态更新是否正确？
```

集成测试会引入真实的模块依赖，有时还会搭配数据库或网络 Mock，所以比单元测试慢，但仍比 UI 测试快得多。它擅长发现的是模块边界上的问题，比如两边约定的接口协议不一致、数据格式对不上。至于一个完整的用户流程能否走通，它就回答不了了。常用的有带网络 Mock 的 XCTest、MockWebServer，以及 Flutter Integration Test。

### 第三层：UI 自动化测试 / E2E 测试

E2E（端到端）测试站在用户的位置，从界面出发，走完一个完整的操作流程，再验证结果：

```
测试脚本做的事：
  1. 启动 App
  2. 输入账号密码，点击登录按钮
  3. 等待首页加载完成
  4. 断言：首页上出现了用户名 "张三"
```

它最接近真实的用户体验，能发现完整流程上的问题，代价是慢（分钟级）和难维护：界面一改版，脚本往往就得跟着改。正因为成本高，E2E 通常只用来守住最核心的业务流程，也就是常说的 **P0 路径**，比如登录、购买、播放。这些流程写成 E2E 用例，每次发版前必须全部通过。

可选的工具不少，各有侧重：

| 工具 | 适用平台 | 特点 |
|------|---------|------|
| XCUITest | iOS 原生 | Apple 官方，与 Xcode 深度集成，不支持 Flutter 层 |
| Flutter Integration Test | Flutter | 官方，直接驱动 Dart 层，跨平台 |
| Appium | iOS + Android | 跨平台，一套脚本两端复用，但配置复杂 |
| Maestro | iOS + Android | 新兴工具，YAML 写脚本，上手简单；iOS 不支持真机 |

对 UMU 这样原生和 Flutter 混合的 App，很难指望一个工具覆盖所有页面，按页面技术栈组合使用往往更现实。我们最终选择了 Appium，并用大模型来降低它的编写和维护成本，具体过程在 E2E 系列中展开。

### 第四层：手动探索测试

最上面一层是人脑驱动的、没有固定剧本的探索，它要发现的是那些"感觉不对"的问题。

这一层永远不会被自动化完全替代。好的 QA 在使用 App 时会产生直觉："这个动画有点抖"、"这句文案的语气怪怪的"、"这个页面返回时好像慢了一拍"。这些都很难写成脚本里的断言。手动探索通常放在新功能上线前和发版前的最终验收阶段。

### 四层之间的关系

| 层次 | 覆盖什么 | 什么时候跑 | 速度与成本 |
|---|---|---|---|
| 手动探索测试 | 少量，凭直觉发现"感觉不对" | 发版前 | 最慢、最贵 |
| UI / E2E 自动化 | P0 核心路径 | 每次发版前 | 慢，维护成本高 |
| 集成测试 | 模块边界 | PR 合并时 | 中等 |
| 单元测试 | 核心逻辑 | 每次提交 | 最快、最稳定、最便宜 |

这四层像一座金字塔：越往下越快、越稳定、越便宜，越往上越接近真实用户，也越慢、越难维护。**一个健康的项目，四层都应该有，数量从下到上递减。** 很多团队恰恰相反，只有最上面两层（手动加少量 E2E），底层几乎空白，结果 Bug 要到 E2E 或手动测试时才被发现，修复成本已经很高了。

## 三、维度二：稳定性测试

功能正确，不代表 App 能稳定运行。稳定性测试回答的是另一个问题："长时间运行会不会垮？"

### 三个核心指标

最直观的指标是 **Crash 率**，也就是 App 在使用中异常退出的频率。行业里常见的参考标准是低于 0.1%，即每千次启动不超过一次崩溃。对 Flutter 混合 App 来说，崩溃还分两层：原生层（Objective-C、Swift、Kotlin）的崩溃和 Dart 层的异常，两者的捕获方式完全不同。

第二个指标是**内存**。我们关心的不只是峰值，还有长时间运行下的趋势：内存是否只涨不跌，是否存在泄漏。在 iOS 上，内存超限的 App 会被系统直接杀掉（OOM），对用户来说和崩溃没有区别。设定阈值时还要考虑 Flutter 引擎本身就有 30 到 50MB 的固定开销。

第三个指标是 **FPS 与卡顿**。60Hz 的屏幕每帧只有 16.67 毫秒的预算，超时就会掉帧；如果帧率低于 15 并持续 3 秒以上，就是最严重的"冻屏"。

### 核心手段：Monkey 测试

稳定性测试的主力是 Monkey 测试。它**不按**剧本执行固定步骤，而是用随机或半随机的方式，大量模拟用户操作，去覆盖开发者从没预想过的操作序列。

```
1 个 QA 用 App 1 小时  vs  机器模拟 1000 次操作序列
     发现已知路径的问题      发现长尾随机路径的崩溃
```

我们使用的是字节跳动开源的 Fastbot。它不是纯随机点击，而是基于模型做智能遍历，会优先去没去过的页面、点没点过的控件，同样的时间能走得更深。

### Monkey 测试与 E2E 测试的区别

这两者经常被混为一谈，但目标完全不同：

| | Monkey 测试 | E2E 测试 |
|---|---|---|
| 目标 | 发现未知崩溃 | 验证已知流程 |
| 操作方式 | 随机探索 | 按剧本执行 |
| 能保证 P0 路径吗？ | **不能** | 能 |
| 适合发现 | 隐藏的崩溃路径、内存泄漏 | 业务逻辑回归 |

Monkey 测试擅长在广阔的未知空间里撞出问题，却无法保证某条具体流程一定被走到；E2E 恰好相反。所以两者谁也替代不了谁，只能互补。

## 四、维度三：兼容性测试

功能正确、运行稳定，换一台手机却花屏了，这就是兼容性问题。兼容性测试要回答的是："这个 App 在目标用户的设备上，都能正常工作吗？"

### 兼容性的三个来源

首先是**系统版本**。iOS 每年一个大版本，总有 API 被弃用、新增，隐私权限机制也几乎每版都在变；Android 的问题则是碎片化，从 Android 8 到 14 同时活跃，各厂商定制 ROM 的行为差异又很大。常见的应对方式是明确最低支持的系统版本，对新 API 做版本判断和降级处理。

其次是**设备硬件**。不同的硬件会带来各自的问题：

```
屏幕尺寸  → UI 布局在异形屏（刘海、挖孔、折叠屏）是否正常
GPU 型号  → 特定着色器在某些 GPU 上渲染异常（Flutter 的 Impeller 渲染引擎尤其需要关注）
内存大小  → 低内存设备（2GB RAM）上的 OOM 风险
CPU 架构  → arm64 vs x86（模拟器）
```

最后是**第三方 SDK**。App 依赖的推送、支付、地图等 SDK，可能在特定系统版本上有自己的 Bug，两个 SDK 之间也可能互相冲突。

### 兼容性测试怎么做？

覆盖面最广的方案是**云真机农场**（Device Farm）。AWS Device Farm、Firebase Test Lab，以及国内的 Testin 等服务商，提供大量真实设备，上传 App、选好设备矩阵就能自动跑测试脚本。缺点是贵，而且远程真机的稳定性不如本地。

成本更可控的是**本地设备矩阵**：购置几台有代表性的设备，比如低、中、高端各一台，再加几家主流 Android 厂商的机型，手动或自动化地测试。

还有一种思路是借助线上**灰度发布**：先发给 1% 的用户，通过 Sentry 观察崩溃率和设备分布，如果某个机型的崩溃率明显偏高，再针对性地处理。

我们目前 iOS、Android 各有一台常驻测试机，只能算兼容性测试的起点。真正的兼容性测试需要多设备并行，这是后续的扩展方向。

## 五、维度四：性能测试

稳定性测试关心"会不会垮"，性能测试关心的是"跑得快不快、用得省不省"。它通常拆成六个方面来看：

| 子项 | 关注指标 | 典型工具 |
|------|---------|---------|
| **启动速度** | 冷启动 / 热启动耗时 | Instruments（iOS）、adb shell am start-activity（Android） |
| **页面渲染速度** | 首屏时间、关键页面加载耗时 | 埋点 + 日志 |
| **内存占用** | 常驻内存、峰值内存 | Instruments / xcrun xctrace（iOS）、dumpsys meminfo（Android） |
| **CPU 占用** | 平均 CPU、峰值 CPU | Instruments / adb top |
| **电量消耗** | 后台耗电、特定操作的耗电 | Instruments Energy Log |
| **包体积** | .ipa / .apk 大小 | Xcode Build Report / bundletool |

性能测试和稳定性测试有不少重叠，内存和 CPU 两边都会采集，但看数据的角度不同。同一条内存曲线，稳定性关心的是"有没有泄漏、有没有被系统杀掉的风险"，性能关心的是"基线是多少、比上个版本涨了没有"。

```
稳定性测试问的是：   "会不会崩？会不会被杀？"
性能测试问的是：     "快不快？省不省？"
```

我们的框架以稳定性为主，但每晚采集的内存和 CPU 数据，同样可以作为性能基线复用。

## 六、维度五：安全测试

安全测试回答的是："App 有没有可以被攻击的漏洞？"这个维度通常由专职安全团队负责，但开发者了解基本的风险类型，才能避免亲手写出漏洞。

移动 App 常见的安全风险有这几类：

| 风险 | 具体问题 | 涉及场景 |
|------|---------|---------|
| **数据存储不安全** | 明文存储密码、Token 在 NSUserDefaults / SharedPreferences | 本地存储 |
| **传输层不安全** | 不校验 SSL 证书，被中间人攻击 | 网络请求 |
| **代码逆向** | Release 包可以被反编译（Android 尤其严重） | 业务逻辑暴露 |
| **过度权限** | 申请了不必要的权限（相机、位置、通讯录） | 权限管理 |
| **第三方 SDK 引入风险** | SDK 内嵌广告 SDK 或数据采集 | 合规问题 |

检查手段大致分三种。**静态分析**是用工具扫描源码或安装包，MobSF 是常用的开源工具；**动态分析**是在运行时抓包（Charles、Burp Suite），检查数据在哪里落地、传输是否加密；**渗透测试**则由专业安全团队模拟攻击，通常在大版本发布前做一次。

安全测试不在我们当前的建设范围内。不过 Fastbot 随机操作的过程中，偶尔会走到一些不应该暴露的入口，比如跳过登录直接打开某个页面，这可以作为一个副产品来观察。

| 维度 | 回答的问题 | 主要手段 | 我们的进展 |
|---|---|---|---|
| 功能正确性 | 功能对不对 | 单元 / 集成 / E2E / 手动探索 | E2E 已落地（LLM 辅助），单元与集成待评估 |

| 安全性 | 有没有可被攻击的漏洞 | 静态扫描、抓包、渗透测试 | 暂未建设 |

## 八、什么时候跑什么测试？

不同的测试，运行成本和反馈速度差别很大，所以应该放在不同的时机触发，而不是全部堆到发版前。越快越便宜的测试，跑得越频繁；越慢越贵的，留给夜间和发版前的专项：

```
每次代码提交（push）
  └── 单元测试（快，<1分钟）

PR 合并到主分支
  ├── 集成测试（中速，5~10分钟）
  └── UI/E2E 冒烟（只跑最核心 P0，5分钟）

每日定时（夜间）
  ├── 完整 E2E 回归（所有 P0/P1 路径，30~60分钟）
  └── 稳定性压测（Fastbot 多账号长时运行 + 性能采集）← 已上线

发版前专项
  ├── 兼容性测试（多设备矩阵）
  ├── 完整性能测试（对比上个版本基线）
  └── 安全扫描（MobSF 静态分析）

线上持续
  └── Sentry 崩溃监控（实时）
```

## 九、AI 改变了什么？

上面这张地图在 AI 出现之前就是这样，测试的分类和目标并没有变。变的是"自动化"的成本结构。

传统 UI 自动化最贵的地方不在于写第一遍脚本，而在于维护：控件位置一变、文案一改，脚本就失效，需要人去逐条修。大模型擅长的恰恰是"看懂界面、理解意图"，这让几件过去很难做的事情变得可行。

**录制和生成用例。** QA 在真机上操作一遍，工具自动抓取每一步的界面变化，再由大模型推断操作意图，生成可回放的用例。写用例的门槛从"会写脚本"降到了"会用 App"。

**用例自愈。** 回放失败时，大模型重新观察失败现场，判断是界面改版导致的定位失效，还是真正的功能问题。前者自动给出修复方案供人审核，后者如实报告。维护成本从"人逐条修"变成"人审核 AI 的修改"。

**探索性操作。** 给 AI 一句自然语言任务（比如"进某门课程把它收藏"），它就能在真机上自己摸索完成。这要求 AI 能以很低的延迟读取界面、执行动作，我们为此专门做了一套注入式的直驱方案，单步从秒级压到了毫秒级。

**问题分析。** 崩溃堆栈的归因、线上崩溃按机型和版本的分布分析，都可以交给 AI 先做一轮初筛，人再看结论。

AI 没有改变的是：测试的目标仍然需要人来定义，断言是否合理仍然需要人来判断，而大模型本身的不确定性，也意味着关键路径上仍然需要确定性的回放和人工复核。这个系列里的大部分篇幅，讲的正是怎么在"AI 的灵活"和"测试的确定性"之间找平衡。

## 十、我们团队现在在哪里？

诚实地评估现状，才能知道下一步投资哪里：

| 测试类型 | 现状 | 优先级 |
|---------|------|--------|
| 稳定性测试（Monkey） | **已上线**：iOS / Android 每晚定时运行，iOS 多账号长时压测，失败自动推送告警 | — 持续优化覆盖率 |
